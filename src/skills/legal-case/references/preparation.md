# 通读准备与事件认定读手

输入：本案全部当前材料和条款、冻结词表、已有概要及事件（增量时）、输出文件路径、数据格式说明。通读全部材料形成案件概要；统一认定合同用作条件或时间基准的事项，判断粒度、同一性和必要参与者。名称相同本身不等于同一事件。事件所需主体先确定或同批建立。

## 顺序通读与带问题回读

1. 用固定文本版本及完整条款建立阅读目录，列前言、article、签署、附件与表格；区分已提供材料和仅引用材料。目录和笔记保存在主会话分配的合同 `tasks/` 路径，每个范围初值未读，不用“未发现异常”代替实际阅读记录。
2. 按原文顺序阅读。长文按完整 article 分窗，单条超过窗口则分连续片段，保留标题、条款ID／版本和范围，不另建提取主责。每窗记称谓、包／阶段、定义、条件／时间基准事项、跨条引用及待核对点，并附原文位置。
3. 带具体问题回读关联条款及已有记录。说明要解决什么，每项最终标明找到依据、材料未提供或原文歧义。两个包的同名事项先核对包和阶段；报告、完成事项、证书签发有不同条件或被分别用作时间基准时，不能仅因名称近似合并。不假定合同事项已实际发生。
4. 汇总原定概要、主体和事件提交。全部已提供范围有阅读记录、待核对项有明确处置、概要／事件可定位原文后结束准备。该条件不表示全部规定已完成业务提取；前置准备的 covered_clauses 仍为 []。

主体包含前言和签署中有明确角色的代表；原文称谓及已有地址需可供后续读取。事件描述保留影响发生认定的共同前提、包／阶段、参与者和来源，区分“知悉”与“事实发生”、“事项完成”与“据此发证”。含义有歧义时保留措辞与问题，不用名称补造条件。

产出 `phase=preparation` 的完整写入 JSON，`covered_clauses=[]`，可带 `overview:{text_versions,body,authored_by}`；records 包含带出处的 event 节点、主体、锚及相关引用。返回输出路径、记录数量和问题摘要。前置事件不宣称条款已完整提取。读手只写分配的文件，不直接改数据库。

成功 write 后，主会话交付完整 query 记录：data、正式 object_id／record_id、evidence、provenance；事件的 description、participants 及已给出的包／阶段不可简化成仅 ID／name。所有分页读完，空事件清单显式保存；输入位置和正式任务契约见 `handoff.md`。
