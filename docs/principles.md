# 法律关系建模底座 — 方向、原则与概念设计

> 本文是项目的定向文件：系统陈述方向、原则与概念设计，供 design.md、spec.md 与开发对照。推理过程、讨论轨迹与被否决方案见 pre-design.md，此处只留结论及其理由。代码统一放 legal/src；用户已要求转入实现，见 decisions.md §1.34。

## 一、项目定位与边界

> 基础设施性质的底座，只考虑一个问题：针对某特定合同做精确建模。

**它是什么**：把一份合同的建模所需全部素材转化为 SQLite 中带溯源锚的结构化权利义务关系记录——读库即读合同，且每条记录能翻回原文。"对商业世界的法律关系做精细化建模"是本体层主张（单元与槽这套关于合同的一般学说）；实例层的工作对象始终是一份特定合同。

**它不是什么**：

- 不是应用，不服务单一场景。合同审核、履约跟踪、争议支持、尽调比对，都是将来的租户
- 排除：抽取体验、审核逻辑、UI、签署流程、CLM 一概不做
- 边界：只管"合同文本规定了什么"，不管"实际发生了什么"。判断违约=拿实际发生的事实对照合同规定，是消费方的工作、需要两份输入，本项目只提供其中"合同规定"这一份

**第零条判定法**（底座边界的操作性标准）：

> 凡是只在"读模型的人"那里才存在的问题，都不是建模层的问题。

两个被它挡在门外的假问题，理由留档：

- **合同群**——多份素材属于同一张图，当且仅当它们构成同一份合同的文件整体（正文+补充协议+附件+从属文书如保函）；围绕一个主体的跨合同组合、主体级汇总，是消费方的工作，本底座不提供跨合同数据查询（词表层的聚合除外）
- **法域**——上层按商业世界的认识分类，法域差异只落在基层词表的扩展上。更深的理由：本模型是描述性的（记载文本规定了什么），法域是评价性的（这条款效力如何）——评价是消费者的问题。实证：三份规则文件（中国法采购×2、FIDIC）主题结构完全平行

**时序边界**：项目原生的时序结构是文本的序列——版本先后与登记序——一个偏序（家谱），不是钟；建模层没有时刻。补充协议的先后不建机制：各素材条款并存入库，明示的修改关系本身是一条规定、由提取记为引用表的指向，不明的并存为冲突，折叠出"现行有效文本"是消费方的投影。"某时刻哪些规定生效"拆开是三件事：沿修改指向折叠出有效文本、相关事件何时发生（世界）、规定自身的时间性内容——最后一样由"时"形态槽值表达（是内容不是维度），前两样天然在消费方手里，把家谱映射到钟上是消费方的投影。

**资产寿命排序**：本体（词表形制）> 代数（查询/diff/聚合）> 实例库 > 提取管道（最短命，随时可换）。

**对消费方的承诺**（验收主张）：三份既有规则文件的每条检查项，都必须能表达为本模型上的查询。

## 二、建模对象：法律关系的概念结构

### 2.1 从一句话看原子

> "卖方须在收到预付款后 30 日内向买方交付设备，迟交超过 4 周的，买方有权解除合同并按合同总价 10% 索赔。"

拆开是三个关系，以及事件和定义值的引用：

- 关系一（基础义务）：卖方对买方的交付义务——时限是"某事件后 30 日"
- 关系二（权力）：买方的解除权——由"迟交超 4 周"这个条件触发
- 关系三（二级义务）：卖方的赔偿义务——算式=合同总价×10%，由同一条件触发
- 事件一："收到预付款"——它本身是另一关系（预付款义务）的履行
- 定义值："合同总价"——被算式引用的、别处规定的值

由此得到原子式：

> **一条当事人关系 =（两个主体〔各自 id＋性质〕；可选模态；行为类；细节{槽:值}）**

### 2.2 原子的各字段

**当事人**。当事人之间的每条关系记录两个主体及各自性质；多方安排按合同实际规定拆成二元关系，不枚举全部两两组合，且保留共同金额、条件及相互影响。合同级规定仍用合同单主语结构。性质分两层：

- **核心性质**（独立于模态，封闭在代码）：义务人/受领人、行使方/承受方、享有方/相对方、受保护方/受限方八种。不按语法主语强制确定端点，不先填模态再推性质（decisions §1.10）。
- **功能标签**（按文填写的开放实用标签）：申请方、被保证方等。标签不用于给一条二元关系添加第三个端点。

配套两条：双务条款拆两条记录（"双方互负保密义务"=各做一次义务人/受领人）；**交易角色与关系性质分清**——买方/卖方/银行是交易角色（主体识别层），义务人/行使方/申请方是关系性质（挂在当事人引用上），同一买方在交付义务里是受领人、在解除权里是行使方。

**模态**。保留义务、权力、许可、豁免四种定义，作为可选辅助分类。空值只表示未分类，不表示无义务或无约定。不以情态词映射机械验证分类正确性；已填分类仍须有依据。当事人性质、行为类、细节和引用须完整表达规定；肯定与否定通过现有槽和值结构表达，不另加统一字段（decisions §1.3、§1.15）。

**行为类（交易单元）**。开放词表，指向词表第一层（付款、交付、验收、保密、保函……），律师治理。

**细节（槽值）**。值只有六种基本形态，封闭、写死程序：

| 形态 | 内容 | 例 |
|---|---|---|
| 量 | 数值+单位（单位取自工具自带的单位配置，见 §七） | 100 万美元、0.5% |
| 时 | 绝对日期 / 相对事件（+30日）/ 期限（起事件→止事件） | "收到预付款后 30 日内" |
| 条件 | 布尔表达式：算子{与/或/非}+阈值比较+计数修饰（连续N次、X期间内），叶指向事件/单据/期限/量 | "迟交超过4周""连续两次验收不合格" |
| 算式 | 引用其他值的计算式 | 总价×10%、LPR×2 倍 |
| 名/文本 | 原文表层+归一化字符串；枚举=名/文本+槽条目声明的值域（值域是词表内容，律师治理） | 交货地点=上海港、方式=书面、结算=分期 |
| 引用 | 指针，指向素材/附件/术语定义/定义值，可顺着跳查 | "规格见附件A""标的物为附件一所列设备" |

复杂值由六种基本件拼装，如付款安排=重复组`[{阶段名, 比例, 前置条件[]}, …]`。拼装语法在程序里，工具校验拼法。但书（"作为付款条件，但不作为质量最终依据"）**不是值形态**——它是作用域限定，见 2.4 的除外记录。

### 2.3 关系如何连接：事件与解释性指向

条件和相对时点中用到的发生事项，以引用指向**事件节点**；事件可与另一条关系的履行相联系，例如交付义务与交付完成。金额比较、次数要求、时间偏移及逻辑组合保留在相应的条件或时间表达中。

**事件的粒度与引用（2026-09-25 裁决，见 decisions.md §1.6）**：以合同实际用作条件或时间基准的一项发生事项为单位。过程内部的步骤，只有被合同另行用作条件或时间基准时才分别建立节点。“验收合格后付款”使用一个验收合格事件；“检测完成后三日内出报告，报告送达后五日内付款”分别使用检测完成、报告送达两个事件。“验收合格且收到发票”引用两个事件并表达“且”；同一交付事项后的十日、三十日分别在时间表达中记录偏移。

事件是节点表中的独立记录，具有**案件内唯一 ID、出处锚及必要的参与者引用**。同一事项多处使用时复用同一节点，不同事项分别记录；同一性根据原文所指判断，结合参与者、对象及批次或阶段等信息，名称或参与者相同本身不构成自动合并依据。各法律关系通过条件或时间细节引用事件。事件识别与入库前置于打标分组，后续读手取得共用事件记录并直接引用，见 §8.3。

事件记录描述合同约定的发生事项；实际是否发生及发生日期由消费方结合现实事实处理。由此：

- **救济不需要专门机制**：违约金、解除权是合同约定条件触发的二级关系，与基础关系同一形状、同一存法
- 一份合同在这个模型里包含基础关系、它们的条件与时间内容，以及事件等共用引用对象

图里除了关系边还需要两类支撑节点：**事件**（条件与时点的指针对象）与**定义事实**（"合同总价=××"这类单主体记录，供算式和条款引用）。

补充协议的先后与取代**不建机制**——重组不做文本手术，各素材的条款并存入库（正文第 5 条与补充协议的改条同时在场）。明示的修改关系本身是一条规定，提取时记为引用表的指向（旧条款→新文本，各带各的锚）；不明的并存为冲突——冲突即风险点。折叠出"现行有效文本"是消费方的投影。新补充协议到达后，经预处理登记、切条款，再通读、识别事件、打标分组与提取（可重放）；一般修正与重跑的具体实现见 decisions.md §2.2。"附件与正文不一致以正文为准"这类优先次序条款是解释规则，入库为以合同为主语的元规定（见 2.4）。

### 2.4 合同节点与元规定

合同本身是第五类节点。它自己的基础记录：当事人与角色绑定（"买方=某某公司"，锚指向首部/签署栏——签署栏因此**不是**"无规定内容"）；文件构成（这份合同由哪些素材组成：主合同、补充协议、技术附件——法律上的一个合同可以跨多份素材，与素材表里的物理文档分清）。

**元规定 = 以合同节点为主语、带锚的记录**——不构成当事人之间的二元关系、作用于合同整体的那些规定都有了家：

```
合同00001.生效条件 = 双方签章且买方收到履约保函（锚：第11.1条）
合同00001.定义.设备 = 主机及附件（锚：第1.1条）——文本型定义，供其他条款引用
合同00001.可分割性 = 部分无效不影响其余（锚：第13条）
```

除外与条间优先也落这里：以合同（或所在条款）为主语的记录，值=双指针，指向走引用表——"作为付款条件但不作为质量依据"=（算作→付款条件，不算作→质量依据）。

三个便宜：①单元判据顺势推广——记录的主语可以是当事人，也可以是合同（"合同00001有一个生效条件"问得出口；词表里自然出现一族以合同为主语的"合同机制类"单元：生效条件、文件构成、定义、争议解决），先前"合同文件构成"过不了自身判据的矛盾解开；②作用域=合同全部，由"作为合同的属性"这个位置隐式表达，不需要另建作用域边；③复用单主语记录模式（定义事实本来就是这个形状）。

### 2.5 三层结构与两层词表的咬合

描述一个法律关系至少三层：主语（当事人组，或合同）、关系类（什么性质）、类中细节（如何具体）。抽掉任何一层都不再是规定的描述。与词表的对应：

> **词表 = 抽掉主语的三层结构**（无主语的"类+槽"形制）；**账本 = 补上主语的实例**（槽值带锚）。第三层内部再切一刀：槽形制归词表（律师领域），槽值归账本（带锚）。

## 三、两个不变量（质量的定义）

### 3.1 完备性（无漏项）

读库可以读到合同文本的全部信息——底线由存储保证：原文整篇在条款表里，从登记那一步起就在库中，不依赖归类。归类是长在其上的第二层，语义完备不可机械判定，故按两层诚实分账：

- **条款级（机械可判）**：每条条款至少有一条锚在其条款内的记录（含"无规定内容"记录**或缺口记录**）——归类覆盖查正向，缺口在打标（无匹配）与提取时即显式入库；每条关系/细节/元规定记录的锚必须落在某个条款内——反向。不满足即对账报告上的缺口行
- **断言级（不设检验）**：一条条款内的全部规定点是否都被表达（含词表缺口导致的漏项）——机械无判据，也不设模型互查；质量由验收考卷间接度量，错误在使用中发现

事件漏提同样属于一般提取质量风险：它可能影响条件与时间基准的表达，条款覆盖通过不表示事件已经提全。当前接受该风险，不增加事件专门检查或补提流程，不再将其列为事件机制的独立待决问题；后续若实际验收暴露出明显问题，再据具体表现讨论调整（2026-09-25 裁决，见 decisions.md §1.7）。

归类的去向：规定进关系与细节，主体/事件/定义值/外部基准/合同进节点，合同级规定进以合同为主语的元规定记录，"以下简称"进别名声明，"这段无规定内容"（页眉、页码、目录）本身也是一条机器归类（签署栏除外：当事人与角色绑定出自那里，见 2.4）。词表装不下的规定点不硬塞——写入缺口表并回流（见 5.4）。

前后矛盾的两条记录并存展示——冲突即风险点，裁决留给人（不裁决铁律）。

### 3.2 忠实性（无添加）

库里没有任何文本之外的东西。绝对无添加不可能（切条款、赋槽值本身就是解释），可执行的标准是三级来源、**永不混层**：

| 来源级 | 必须伴随 | 例 |
|---|---|---|
| ① 原文引述 | 锚（引文必须真实存在于文本） | 值="收到预付款后30日内" |
| ② 机械变换 | 锚 + 表层形 + 格式契约串 | 表层"1,234.50 USD"→归一 {1234.50, USD}，契约 "0,0.00 CCC" 随行存，写入时跑往返验证 |
| ③ 显式推断 | 前提（前提须能追溯到锚定记录）+ 责任人 | "第3.2条与第5.1条所指质保期应为同一期间——前提：……——责任人：张律师" |

第③级是"不允许无源信息"的人工通道（推断写入时即带前提与责任人署名）。查询可按级过滤；机械可验的是引文存在与已声明的格式变换。模态分类、关系归类及其语义正确性属于理解判断，不能因来源级为①②就宣称其已被机械证明，质量由验收考卷间接度量。

### 3.3 出处：第四正交维

每条主张——当事人组、关系类、每一个槽值——都必须有来头。来头的形态随来源级不同：①②级的来头=锚，指回原文的具体文句；③级的来头=前提（前提本身可追溯到锚定记录）+责任人。三个内容层之外，这是忠实性不变量强加的正交必备维：**权威永远在文本那边，库是永远可被文本反驳的下属物**——推断也必须把它的文本前提摆在明处。

## 四、案件库的存储面（概念级）

一个案件 = 一个 SQLite 文件 = 一份合同的建模所需全部素材：合同正文及其组成部分（补充协议、附件），以及为它出具的从属文书（保函等）——再远的关系（框架协议、该主体的其他交易）是别的案件。库的表分两组：

**关系图五件套**：

| 表 | 装什么 |
|---|---|
| 关系表 | 当事人二元关系的两个主体〔各自 id＋性质〕，或合同级规定的合同主语；可选模态、行为类、来源与出处。时间性是内容（"时"形态槽值），原文版本由锚固定；记录修正另有追加版本——不设法律上的"有效范围"元字段 |
| 细节表 | 关系id、槽名、值、值形态、来源级、表层形、格式契约串、锚 |
| 节点表 | 主体 / 事件 / 定义值 / 外部基准 / 合同。**主体=有独立 id 的法律主体**：规范形（全称）+**别名集**（每个别名带绑定锚与来源级——合同声明的①级、未声明共指的③级指称绑定；行存储在引用表，节点呈现为集）。**同一性核查=比 id 相等**：关系行当事人组存主体节点 id，别名集与绑定行是提取理解的依据与审计痕迹，不是运行时解析层；事件所需主体在前置识别时先确定或同批建立，其余称谓在后续提取时判定。**事件=案内唯一 ID 的独立节点**，带出处锚与必要参与者引用；粒度及同一性按 §2.3，在打标分组前识别并入库供各读手引用，具体字段形式待设计。定义值带完整出处（来源级+锚）；外部基准（LPR、汇率、指导价）只记被引用、永不记数值；合同节点带当事人与角色绑定（锚指首部/签署栏）及文件构成，元规定=以合同为主语的记录（见 2.4） |
| 引用表 | 条件、触发、算式引用、别名声明（"以下简称X"，带锚）、同一性（③级指称绑定——提取判定的依据与审计痕迹；节点重定向——事后合并指认，参与查询折叠）、解释性指向（除外的双指针"算作→A、不算作→B"、条间优先、术语定义引用、修改指向——补充协议明示的"旧条款→新文本"） |
| 锚表 | **引文＋条款地址**（素材/版本/条款；同一引文在条款内重复时加出现序号或加长引文消歧——与法律文书引用原文的方式同构）。**锚指向已登记文本版本的条款**——预处理的转换文本（格式转换/OCR）就是工程化文本，进入建模的文本必须先是它；原始素材是法律权威的档案，但不承担锚的日常指向。链条：记录→锚→条款（素材/版本/序号）→原始素材。可被任何行引用（关系、细节、节点、别名声明）；验证=引文在该条款内逐字可搜得（文本版本整篇在库，搜索为确定性代码）。**连接规则与原文所需的一切仅此；任何加速手段（索引、位置缓存）是实现细节，不入概念设计** |

**证据与流程七件**：

| 表 | 装什么 | 服务哪条原则 |
|---|---|---|
| 素材表 | 案件有哪些文件（名称/类型/哈希/原始文件字节）；原件随 SQLite 移交 | 一案件多文档 |
| 文本版本表 | 每份素材的转换文本（转换方式：格式转换/OCR；重组不产文本版本），进来即不可变，改版加新版本号 | 锚的靶子；原始素材是档案，经由文本版本上的转换链可达 |
| 条款表 | 按合同结构零解释切分（素材/版本/序号/条款文本/**标签**），序号即条款地址；标签初始为空、重组打标填充——unit 多标签，或"无规定内容"/"无匹配"标记；切分零解释、标签后置 | 字符覆盖审计；打标覆盖闭合（范围内无空标签行）；分组导出的数据源 |
| 词表快照（三张） | 开工拷入的单元/槽/归属，开工即冻结、案内不改 | 案件自含 |
| 出身表 | 开工时间、加载的词表文件名+内容哈希、格式版本（模态表、值形态语法、单位配置、案件文件格式）（钟值属案卷管理，建模用的是顺序） | 版本戳 |
| 缺口表 | 归类层缺口的指认：条款id、类型（未归类/疑似缺槽/疑似缺单元）、描述、锚、提出者、时间。**写入即定、只读、无状态流转**——内容本体在条款表，这里只记"哪条缺什么格子"；不参与任何生效流程 | 无漏项的库内账本 |
| 案件概要 | 商业模式总结（重组步串行读手产物，一页：交易性质、当事人角色链、主干流程、资金担保结构、特殊机制、素材地图）；只描写交易、不描写标签体系；随重组批次重新生成 | 读手上下文的库存份（不是库的主张：不进关系图、不带锚、不设来源级）——并行读手共同背景、可重放与审计 |

出处机制覆盖任何行：关系表、细节表、定义值节点各带来源级与出处指针，锚表可被任何行引用——与 3.3 的"当事人组、关系类、槽值三层主张都有来头"对齐；"合同总价=100万"这类定义事实由此可查依据。**存储纪律：追加式**——对象 ID 稳定，修正新增完整记录版本及取代指向，默认读最新版本，历史及原文锚仍可查询；条款补标签也追加版本。误提对象追加撤销版本，拆分则撤销旧对象、新建对象并同批修正现存业务引用（decisions §1.16、§1.20）。文本版本不可变、缺口表只追加不流转的纪律继续适用。字段级 DDL、来源与引用细则见 design.md；同素材重转换登记新文本版本，旧锚不动。

## 五、两层词表：概念与治理

### 5.1 两层的定义

**交易单元（unit）**：商业交易的基本行为单元，按商业世界的认识分类——付款、交付、验收、质量担保、保函、保密、变更、终止、争议解决。慢变、跨合同种类、跨法域共享，量级以"一屏可览、一名律师可持"为限。

判据一句话：**"谁对谁有一个X"（或"合同X有一个Y"）问得出口的是单元**。交付、预付款、保函、保密撑得起"谁对谁"的骨架；生效条件、文件构成、定义以合同为主语问得出口（合同机制类单元）；比例、期限、上限问不出口，只能依附（"付款的比例"）。条款标题≠单元（"质保期"常做标题，但它是质量担保的时长参数）。

单元三资格，缺一不可：主题检验（语料中确有以它为主题的条款）、关系检验（谁对谁）、跨种类检验（在多个合同种类中作为主题出现）。

**规定槽（slot）**：单元之下可以设立的规定维度——付款单元下的阶段比例、前置条件、时点、上限。快变、按需生长。两资格：依附检验（离开单元无独立意义）、参数检验（限定一项安排而不构成安排）。**槽空着是合法状态且本身就是信息**（合同没约定违约金上限=审核发现）。

分界一句话：**词表管单元和槽，账本管值。**

### 5.2 三种词表、两种命运

- 模态（约四种）：封闭，写死程序
- 值形态（六种基本件+拼装语法；但书不是值形态，见 2.4 除外记录）：封闭，写死程序
- 行为类与槽条目：开放，律师治理——**唯一需要治理管道的部分**

### 5.3 结构：归属、通用槽池、吸并与裂变

- **归属多对多**：一槽可挂多单元；完全不挂归属的槽入**通用槽池**（时点/地点/方式/但书），任何单元可用——对应 FrameNet 的核心/周边区分：周边共享、核心专属
- **吸并优先**：细类差异装得进"同一条边上的参数"就吸并（进度款/到货款=付款单元的阶段槽取值）；踩了三条硬线才准独立：
  1. **换了当事人**——预付款保函是银行↔买方的边，塞不进买↔卖付款义务的参数（槽描述一条边，挂不上第二个当事人）→保函独立成单元（预付款/履约/质保保函是类型取值）
  2. **原“换了模态”判据已撤回**——模态可选后，不能凭该字段变化决定拆分。应依据原文是否规定一项独立的权利义务判断；具体单元吸并与裂变仍由初始化和治理中的律师审定，不由机械规则决定
  3. **条件适用槽成堆**——"仅阶段=预付时可填"的校验规则攒多了=用 if-else 重造类型系统 → 裂变时机
- **裂变有据**：条件槽攒成堆→细类独立成单元→补"原属"谱系字段（历史可追；快照隔离下改的全是全局词表与未来案件，旧案数据一个不碰）。上位关系（is-a 层级）不建，聚合查询用槽取值走通

删除单元导致槽失去全部归属时，须在同份变更中明确删除、改挂其他单元或改为通用槽，不自动降为通用槽（decisions §1.22）。

### 5.4 治理

**词表治理 skill 总体流程已收口（2026-09-25，见 decisions.md §1.9）**：治理是低频、按需的活动，入口为案件缺口汇总或律师主动提出变更。agent 对照当前全局词表与相关证据，将具体建议、理由及证据写入文件；人工直接在文件中写意见；agent 按意见整理变更内容，由主会话调用词表 CLI 执行并输出变更摘要。自然语言意见即可，无需精密的流程设计。案件缺口可能已被后来的全局词表更新解决，须结合当前词表判断。

- **槽是耗材，单元是观点**：单元清单=词表作者对"商业世界由哪些基本安排构成"的理论主张。单元错的代价是系统性的（碎片化拆散查询、两个作者两套单元图就分裂）；槽错是局部的
- **词表出生只有一个通道：全局、律师、经词表工具**。案内不造——机器不造，也没有案内人手补条的偏门；新增与管理字段是大操作，不属于办案途中。案内遇到词表缺口：规定入库到能入的深度（关系能建则建），装不下的维度写入**缺口表**——写入口两个：打标时的无匹配（疑似缺单元）与提取时的疑似缺口（疑似缺槽等）
- **聚合=缺口的回流口**：扫各案缺口表汇成词表缺口报告（缺什么槽、缺什么单元，各带条款与锚），律师过目后在全局增删——单元深审（审的是世界观），槽快审（错了代价局部）。旧案不回填；案件缺口多到影响使用，救济是重开新案（新快照、新案件文件，提取可重放，代价低）
- **裂变是单元增长主通道**，凭空发明是例外
- **纪律：不能改，只能增删**。条目不可变（一个 id 的含义永远只有一份，解释永不漂移）；想"改"=增新条目+删旧条目，新条目可带"取代了谁"（跨案统计时对齐两代概念）；删除发生在全局治理中，由律师决定，缺口汇总与律师主动提案均可发起

## 六、词表的物理形态与流动

**语法裁决（decisions §1.13）**：以下 YAML 文件采用标准 JSON 写法，由标准库读取；不支持 YAML 的额外语法，保持零第三方依赖。

- **文本为源、SQLite 为运行快照**：源=git 仓库里的 YAML 目录（每单元一文件+通用槽一文件，起步可单文件）。选文本不选 SQLite 的理由：词表小、慢变、是律师的长期资产——文本胜在人审（改动即 PR）、历史（git 全套）、协作（可合并）、长寿（纯文本最耐久）；"难手改"是弱保护，真门卫是加载时严格校验
- **开工拷快照**：开工命令读取 YAML→校验（值形态拼法、引用完整）→算内容哈希→整拷进案件 .db；哈希写入出身表作版本戳。案件从此自含，放多少年自己解释自己
- **案件反馈与律师提案进入全局治理**：案件快照**开工即冻结**（与文本版本同等的不变纪律，案件终身相伴）；办案中的词表缺口以报告回流。按需调用聚合命令汇总案件，产出对比报告（词表缺口清单：缺什么槽/单元及证据条款；用法不一；建议废止）；律师也可主动提出变更。两种入口均按 §5.4 形成建议、取得人工意见，再经工具增删全局词表。全局词表以 YAML 及其版本历史保存，旧案不随全局更新而改变
- **工具是词表文件的唯一正门写入口**：绕过工具的手改由加载时校验拒绝、git diff 显形

## 七、系统形态：两组 CLI、两条桥

- **技术选型**：CLI 工具 + 编辑单个 SQLite 文件。一命令一进程干完即退；零依赖纯标准库；无服务器。模型上借属性图思想（带属性的边），不引入 RDF（三段式挂不上属性）与图数据库（要起服务的重型依赖）
- **工具不含内容**：程序只带规矩（模态、值形态两张封闭表）；开放词表是外置"变量"文件，须先加载，没有它工具空转。**换词表内容，工具一字不动；改值形态构造语法=格式变更，工具必须动且格式版本前进**
- **单位配置**：单位表（币种照抄 ISO 4217、期间单位、百分比、计数单位）是工具自带的**配置文件**——标准出生而非归纳出生，随工具版本演进，不是词表内容；开工时其版本/哈希记入出身表。分流判据由此确立：**归纳出生的进词表（单元/槽），标准出生的进工具配置（单位）**
- **命令面按原子动作切，不按流程步骤切**（已裁决）：命令的最小单位是一条完整记录（关系、细节、节点、引用、锚）——来源级与出处是整条记录的属性。流程步骤不对应命令（重组=写标签＋分组导出；提取=把一批记录写进库）。编排负担在 skill 侧，工具只提供可组合的原子动作。**两种调用方式**：直接命令行；以一个 JSON 文件为参数批量输入。skill 中必须包含一个详细讲解工具用法部分
- **预处理组件（独立转换边界）**：统一 CLI 入口调用显式配置的外部转换程序，将其支持的原件格式转为保留段落/表格结构的 `text.txt` 与转换 `metadata.json`，校验后交给登记。实际 PDF/Word/OCR 引擎独立配置，核心工具保留标准库实现；不承诺任意格式自动可用。预处理 skill 只记载和执行调用方法，不做法律判断。转换异常随 metadata 交接，影响阅读的源件问题由调用方处理；**原件转换后先 register，再由案件 split 执行条款切分**，scan_structure 的复用及扫描异常入缺口表均在案件侧。七件交付物的物理位置与统一预处理协议见 spec §1、§9.7
- **读手原则（编排纪律，约束全部 skill）**：凡需要大量阅读合同条款的环节一律用 sub-agent 读手完成，主会话不读全文——整份/整章/整组级阅读必须下放，单条款核查可留主会话。主会话是编排者（切批、派发、收集、校验、写库、看报告），合同正文进入哪个读手的上下文就死在哪，编排质量不随合同规模退化
- **两组命令，各守各的文件**：
  - 案件 CLI（对 .db）：开工（--词表，加载并拷快照）、登记、写记录、查询、对账
  - 词表 CLI（对 .yaml）：初始化、列、查、增（单元/槽，--归属）、删、diff、聚合
- **两条桥，一上一下**：开工（词表→案件，向下拷快照）归案件侧；聚合（案件→报告→词表，向上回流经验）归词表侧。除两条桥外，无任何命令同时碰两种文件
- **节奏两分**：词表工具是治理工作台（慢、人审、低频）；案件工具是日常流水（快、机器干重活、人拍板）。将来词表工具可独立成交互工具，接口就是词表文件

## 八、工序设计

### 8.1 词表 v0 生成：两遍两闸

词表初始版本不是手敲，是两遍两闸的产物（机器起草、两道人工闸）：

**人工交接方式已定（2026-09-25，见 decisions.md §1.8）**：agent 将提取、整理的结果写入文件，人工直接在该文件中写意见，agent 读取意见并整理结果后继续原有步骤。两道人审均采用此方式，自然语言意见即可，无需专门的意见格式或审批机制。

1. **第一遍（宽容生成）**：读手（子 agent）逐条读语料，每条记五样——主题（自己的话，什么粒度顺口叫什么）、可约定的点、原文措辞摘句、当事方、模态词（须/有权/不得）。读手不懂词表概念，只报告不发明
2. **中心裁决**：聚出候选单元清单，逐个过三重资格（主题/关系/跨种类）；**默认动作是吸并**（候选先假设自己只是参数），踩硬线才独立。每条候选附证据（哪些种类哪些条款）、预判（独立/吸并进X/存疑）、"谁对谁"检验结果——预判只辅助排序，人可翻案
3. **闸一（人，深审）**：对着证据包，在候选结果文件中写删并等意见；agent 读取并按意见整理定稿单元表（词表骨架）。宽容生成多提等人删——选择题比回忆题可靠；"吸并优先"等谨慎规矩全部在这一侧执行
4. **第二遍（机械收割）**：拿定稿单元逐单元扫语料，收可约定点（带值形态）、真实措辞例句（顺手长成识别特征）、条件适用标记（=裂变候选）。每单元一子任务，有界、可并行、可单独重跑
5. **闸二（人，快审）**：人工直接在槽的提取结果文件中写意见，agent 读取并按意见整理。槽是耗材，快速过；条件槽标记照单全收留档——这就是词表未来的生长路线图
6. **收尾**：哪都挂不上的条款进残留清单（不许悄悄塞进相近单元）——那是漏掉的单元候选，攒 v2；三份规则文件考卷（检查项逐条可表达为查询）+ 法律文本查漏（民法典通则/CISG/UNIDROIT 通则仅作兜底清单，不从法条造单元——法条按"法律怎么管"切块，不按"当事人在干什么"切块）
7. **产出三件套**：草稿 yaml + 证据包 + 判定表，一起进 git PR

### 8.2 语料：混编

- **多机构范本给结构覆盖**：政府示范文本、行业协会、企业自有、律所、FIDIC 类国际范本——多家专业机构世界观的显式陈列。范本是起草机构做好的"单元-槽清单"：下划线=槽声明，但书与标准条款=默认取值，条款结构=单元清单。空白是槽识别的正确输出（"槽在、值空"），兼作无添加的免费测试——爱编值的提取器在范本上当场露馅
- **真实合同给真实世界**：脏乱输入（扫描/表格/涂改）、谈判后的非标条款组合、值级行为——这三条范本给不了，管道跑顺后用少量真实合同补
- **验收必用 held-out 真实合同**：未参与词表归纳，防泄题

### 8.3 运行流程（七步）

**入库 skill 总体工作流已收口（2026-09-25，见 decisions.md §1.7）**：以下第 1—6 步构成合同入库的总体流程，第 7 步由词表治理按需承接。详细设计阶段已确定各 unit 并行提取，主会话逐文件统一写入（§1.17）；整份失败、成功文件重提及追加式修正规则见 §1.11—§1.12、§1.16、§1.20。

词表就绪是前置状态（git 里的 YAML，见 §五/§六）。此后：

1. **开工**：读 YAML→校验→算内容哈希→整拷进案件 .db 快照；出身表记录
2. **登记**：每份素材先经预处理 CLI（显式配置的转换程序→保留结构的文本及元数据；异常由 skill 处置，扫描质量差到影响阅读则向用户要更好的源件）；素材表+文本版本表（不可变，改版加新版本号）；一个案件可登记多份文档（主合同、补充协议、附件、保函）
3. **切条款**：对每份已登记文本版本按合同结构零解释切分进条款表（扫描方法参照 contract_v3：纯脚本、全行遍历、构造保证不丢不重），标签字段初始为空；切分异常（编号重复/跳跃、疑似无编号条款段）显式写入缺口表；所有条款拼回==全文（字符覆盖查复核）
4. **通读准备与重组**：先准备案件概要及可引用的事件记录，再打标、分组。分组文本由脚本逐字导出，不产新文本版本：
   - **商业模式总结**（串行读手）：通读全部素材条款，产出一页总结（交易性质、当事人角色链、主干流程、资金担保结构、特殊机制、素材地图）——只描写交易、不描写标签体系（可复用、不与打标循环依赖）；入库为案件概要，作全部读手的共同背景
   - **事件识别与入库**（2026-09-25 裁决）：负责事件提取的 sub-agent 统一认定事件，按 §2.3 的粒度识别全合同中被用作条件或时间基准的事项，判断不同条款是否引用同一事项，保存出处与必要的参与者信息。事件所需主体先确定或同批建立。读手产出 JSON，主会话按 decisions.md §1.5 调用案件 CLI 校验、写入，形成具有案内唯一 ID 的事件记录；在打标分组前完成。后续提取 agent 的输入包含案件概要与这些共用事件记录及其出处。事件记录是正式建模产物，案件概要继续作为阅读背景
   - **打标**（并行读手）：逐条款多标签，标签只能取开工快照的单元清单（封闭校验在写标签命令内）；页眉目录类标"无规定内容"；一个 unit 都打不上的显式报"无匹配"→缺口表（疑似缺单元——**单元缺口的第一发现点前移到打标**）；读手上下文＝任务说明＋单元清单＋商业模式总结＋本批条款；批次按条款切、互不相交，逐批写入、失败只重跑本批；覆盖闭合＝打标范围内空标签行为零
   - **分组导出**（脚本）：按 unit 从条款表逐字生成组文件（该单元全部条款、各带条款地址、按条款地址稳定排序）——多标签条款出现在每个所属组，是设计行为不是重复错误
5. **提取**：读手取得案件概要、共用事件记录、负责条款及词表，按组读窗推进，**每条款完整提取一次**（该条款全部规定提全，不受组标签限制——分组是上下文组织、不是语义分割）。前置事件识别不表示整条款已经完成；后续完整提取复用已建事件，不因已有事件记录就跳过该条款，也不承担重新认定事件的职责。规定进关系/细节，条件与时间细节引用事件 ID；其他信息按既有结构进入节点与引用。**其余称谓归入主体当场完成**：合同声明的别名（"以下简称X"）①级、未声明的共指写③级指称绑定（前提+提取器署名）——主体节点带别名集；当事人之间的关系采用二元记录，分别引用主体 ID 并记录当事人性质，模态为可选辅助分类（见 decisions.md §1.3、§1.4）；无规定内容段落记"无规定内容"归类；明示的修改关系记为引用表指向；词表装不下的规定点不硬塞，**当场写入缺口表**。每条记录带来源级与出处。各 agent 输出完整 JSON 文件，返回路径、条款清单及摘要；主会话逐文件调用一次 CLI 校验并写入，成功登记完成，失败交回原 agent 修正后重试。事件漏提按 §3.1 的一般提取质量风险处理
6. **对账**：机械六查（字符覆盖、锚验证、值枚举差异、值往返、**归类覆盖**——正向每条款至少一条记录、"无规定内容"记录或缺口记录，反向每条记录的锚落在某条款内；**称谓闭合**——已识别称谓有主体绑定、出处及可解析目标）。值枚举差异仅作提示，不自动认定漏提；称谓检查不保证发现全部未识别称谓（decisions §1.18—§1.19）。产出报告指向具体记录，修正走已有命令；矛盾绑定并存展示。对账有错误可继续查询、登记及修正，但修正后重新通过前不报告本轮入库完成（§1.21）
7. **聚合**（低频、按需，由词表治理流程承接）：扫各案缺口表汇成词表缺口报告（槽与单元）+用法不一+建议废止，按 §5.4 的建议文件、人工意见与工具执行流程处理；律师主动提案进入同一治理流程。旧案快照不动，缺口多则重开新案。每份合同的入库不以完成聚合为前提。**新补充协议到达**：预处理登记新素材→切条款→通读生成概要并识别事件→打标分组→提取，仍按上述入库步骤提交与对账

查询贯穿全程：检索式（按当事人/单元/槽/来源级），节点重定向在查询时折叠，**缺口清单**一条查询即得。

## 九、测试方法

1. 用户提供多份真实合同（未参与词表归纳的）
2. 机器独跑完整转化流程：开工（加载词表快照）→登记→切条款→通读生成概要、识别事件并写入→打标分组→提取→逐文件写记录，全程人不介入
3. 机械六查全跑（字符覆盖、锚验证、值枚举差异、值往返、归类覆盖、称谓闭合，做在案件 CLI 对账命令）——确定性错误须清零；值枚举差异按提示报告，不以提示数量判失败
4. 考卷作答：三份规则文件的检查项当题，只准查库作答，不翻原文；判分在验收时离线进行（人工或模型判均可，这是验收活动，不是系统机制）——每题三档：可答且对／可答但错（数据有问题，回溯记录）／不可答（词表缺口，回流）
5. 产出报告：六查输出＋考卷判分＋缺口表清单；人只看报告
6. 词表改进后复跑同一方法，数字对比即版本进步的度量

## 十、交付物与开发顺序

**交付物=可复用的机器，共七件**：预处理 CLI（统一调用已配置的转换程序，产出文本及元数据）、预处理 skill（薄壳——仅记载工具调用方法，不含智能判断）、案件 CLI（含开工加载词表、对账及条款切分）、词表 CLI（含聚合）、案件 skill（入库编排）、词表 skill（治理编排）、初始化 skill（两遍两闸）。机器跑出来的东西（词表内容、案件库）、过程文档（design.md）、demo 与测试均非独立交付物——"工具不含内容"的延伸。

**物理交付（2026-09-26）**：七件组成 `legal/src` 一个完整目录。相对该根目录，三个 CLI 入口为 `legal/preprocess_cli.py`、`legal/case_cli.py`、`legal/vocab_cli.py`；四个 skill 目录为 `skills/legal-preprocess`、`skills/legal-case`、`skills/legal-vocab`、`skills/legal-initialize`，每个目录有 `SKILL.md`。它们共用 Python 实现和 `references/` 中的工具说明/数据格式，整体可移交。首版保持宿主通用，按源路径及引用关系注册四个 skill，不要求特定宿主专用安装布局；案件数据、词表和任务产物保存到调用方指定的位置。完整路径、资源与注册条件见 spec §1，裁决见 decisions §1.31—§1.33。

**开发顺序**：design.md → yaml 格式定义与校验器 → 初始化 skill（跑出 v0 词表，解锁其余工具）→ v0 词表 → 案件工具完整可用。

**规格细化（2026-09-25）**：design.md 与 spec.md 共同构成开发依据，当前不开始实现。所有生产、测试、SQL和辅助代码位于 legal/src。用户补充确认误撤销可追加版本恢复、缺口固定发现时版本、有原文依据的值留空统一允许 null、历史关系展开当时细节；见 decisions §1.25—§1.30。扫描器源码已按用户提供的 contract_v3 路径核对，原定四项适配及验收规则见 spec §12。
