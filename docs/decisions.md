### 1.1 命令面按原子动作切，两种调用方式（2026-09-16 用户裁决）

裁决内容：

- 命令按**原子动作**切，不按流程步骤切
- 两种调用方式：一是直接使用命令行命令；二是**以一个 JSON 文件为参数，批量输入命令**
- skill 中必须包含一个部分，**详细讲解工具用法**

由此推出的结果（如无异议即按此理解）：

- 命令的最小单位是**一条完整记录**：关系、细节、节点、引用、锚。来源级与出处是整条记录的属性，半条记录既无法定义也无法验证
- 流程步骤不再对应命令。按后续已确认流程，重组表现为写入标签和分组导出，提取表现为一批记录写入；不再生成合并文本版本。principles.md 中"命令面与运行流程七步对不上"的问题随之消解
- 编排负担落在 skill 一侧，工具只提供可组合的原子动作

当时带出的 JSON、依赖与重复执行问题，现由 §1.11—§1.12、§1.23 及 design.md §7、§14—§15 落实。

### 1.2 追加式存储（2026-09-16 用户裁决）

裁决内容：采用**追加式存储**。

推论与含义：

- 记录写错时不改写旧行，新增一行并标出它取代了谁；查询时折叠到最新
- 与库内既有的不可变纪律一致：文本版本进来即不可变、改版加新版本；缺口表写入即定、只读。本裁决是把这条纪律贯彻到全部记录

当时带出的版本、取代、对账范围和修正路径问题，现由 §1.16、§1.20 及 design.md §8、§12—§13 落实。旧“重新合并文本”表述随分组导出方案撤回，新增材料沿既定入库路径处理。

### 1.3 模态保留定义，作为可选辅助分类（2026-09-24 本轮讨论结论，用户要求记入）

判断与定位：

- **模态保留定义，作为可选的辅助分类字段**。义务、权力、许可、豁免作为现有分类口径保留，不要求所有合同规定都套入四类。模态为空只表示未作这项分类，不能据此认定没有义务、没有约束或合同未约定。
- **取消“情态词映射＋机械检测”对模态正确性的验证**。检查“应当”“有权”“可以”等词是否存在、分类是否符合预设映射，只能证明引文存在及映射一致，不能证明分类符合整条规定的含义。模态分类属于理解判断，不再列入机械可验的内容；一般的出处要求仍适用。
- **当事人性质是当前关系结构的基础字段**，表达某主体在这条具体关系中的地位，须与买方、卖方等交易角色区分。义务人/受领人、行使方/承受方等性质已经承载一部分关系性质，因此模态在这些记录中存在信息重复。当事人性质应能独立填写，不以先填模态为前提。
- **模态可选的前提是关系含义仍被完整表达**。不填写模态时，当事人性质、行为类、细节和引用仍须准确表达合同规定；仅将字段改为可空，不能证明这一要求已经满足。

判断依据与边界：

- 项目必须保留合同规定的性质差别，但不由此推出必须使用独立、必填的四值模态字段。模态具有统一分类的便利，不应成为关系能够被建模的必要条件。
- 当事人性质的基础地位，不自动证明现有八种标签及“恰好一个核心方”“核心方等于句子主语”等附加规则成立。当事人地位、数量及关系拆分应依据合同内容判断，不能只由模态字段决定；具体规则仍需明确。
- 量、时、条件、算式、名/文本、引用提供了承载商务条件的能力，但尚未证明具体词表及组合规则足以完整表达所有商务条件。行为的肯定与否定、局部除外的作用范围、分批履行中的事件与关系对应，仍需结合其余字段核实，不能因保留或填写模态而视为已解决。

本项修正此前“模态机械可验”及模态必填的判断；相关结构细化见 §2.1。

### 1.4 当事人之间的关系统一拆解为二元关系（2026-09-24 用户裁决）

裁决内容：

- **无论一项安排有多少参与方，当事人之间的关系均拆解为两两之间的关系，以二元关系作为统一记录单位**。每条记录表达两个主体之间的一项具体关系，并记载各自的当事人性质；多方参与不要求一条关系记录挂多个当事人。
- **记录条数由合同实际规定的关系决定**。三方不必生成三条关系，也不按参与人数枚举所有两两组合；不生成原文未规定的关系。
- **拆分后必须保留多条记录共同表达一项商务安排的联系与约束**，包括共同金额、条件、履行或权利行使对其他关系的影响等。通过细节、条件、事件和引用表达这些内容，不能把原本相互关联的安排改写成彼此独立的义务。
- 当事人性质仍是基础字段，模态仍按 §1.3 作为可选辅助分类。本项处理当事人之间的关系；合同级元规定、定义事实等按已有记录形态表达。

例：“甲乙共同向丙支付100万元，任一方付清后，双方均不再承担该项付款义务。”

- 拆成甲对丙、乙对丙两条付款关系。
- 两条记录共同对应同一笔总额100万元，并保留“任一方付清，两条义务均终止”的条件；不能记成两笔各自独立的100万元付款义务。
- 该表述本身不要求另造一条甲乙之间的义务。

由此收口独立评审问题1：采用二元记录后，多个义务人不构成框架无法记载的理由；后续明确的是多条二元记录之间的关联与共同约束如何落入既有结构，不再因参与方数量而要求多方关系记录。此项也不构成对“核心方等于句子主语”规则的确认。

### 1.5 提取 agent 输出文件，主会话逐文件调用 CLI 写入（2026-09-25 用户裁决）

裁决内容：

- **提取 agent 输出完整的 JSON 批量写入文件**。合同含义的判断、关系拆分和字段填写在输出前完成；文件包含本次提取所需的节点、关系、细节、引用、锚、缺口或无规定内容记录，以及覆盖的条款清单。记录内容完整，相互引用明确；已有对象引用其 ID。
- agent 保存文件后，向主会话返回文件路径、负责的条款清单、产出数量及需要处理的问题摘要。
- **每份提取结果文件对应一次案件 CLI 批量写入调用**。主会话负责发起调用，CLI 负责读取文件、执行校验和写入、返回结果。
- 成功后由主会话登记完成；失败则将具体错误交回原提取 agent 修正文件，再提交重试。
- “主会话统一写入”的职责是提交和结果处理。unit 仍是阅读分组依据，负责条款中的全部规定须按已有原则提全。

本项裁决限于提取产物与提交分工。事件的前置识别与共享随后由 §1.6 确定，入库 skill 总体工作流由 §1.7 收口。具体提取调度、其他共享对象的引用与传递、JSON 结构、新记录之间的编号与引用、批量失败的写入边界及重复提交语义留到具体设计。

### 1.6 事件节点的粒度、引用与分组前识别（2026-09-25 用户裁决）

裁决内容：

- **事件以独立节点记录，具有案件内唯一 ID**。具体法律关系通过条件或时间细节引用事件节点；同一事项在多处使用时复用同一节点与 ID，不同事项分别建立节点。事件描述合同规定中被引用的事项，实际是否发生及发生日期由消费方结合现实事实处理。
- **粒度以合同实际用作条件或时间基准的一项发生事项为单位**。过程内部的步骤，只有被合同另行用作条件或时间基准时才分别建立事件节点。例如“验收合格后付款”建立“验收合格”；“检测完成后三日内出报告，报告送达后五日内付款”分别建立“检测完成”“报告送达”。
- 组合与时间修饰留在相应表达中：“验收合格且收到发票”引用两个事件并表达“且”；“交付后十日付款、三十日提交报告”复用同一交付事件，分别记录时间偏移。
- 同一性的判断依据是原文是否指向同一事项，结合参与者、对象及原文区分的批次或阶段等信息；事件名或参与者相同本身不构成自动合并的依据。各记录保存原文出处及必要的参与者信息，具体字段形式留待设计。
- **在按 unit 打标、分组之前完成事件识别与入库**。顺序为：切条款 → 通读全部素材，生成案件概要并识别事件 → 主会话调用案件 CLI 写入事件记录 → 打标、分组 → 各 unit 的 agent 使用概要及事件记录提取法律关系。事件引用的主体须先确定，或与事件在同一批记录中建立。
- 前置识别以全合同中符合上述粒度标准的事项为范围。识别结果须形成带 ID、出处和必要参与者信息的可引用记录，并实际提供给后续提取 agent。文件提交与错误返回沿用 §1.5；案件概要继续作为阅读背景，正式事件记录遵守出处要求。本项采用已有节点与引用结构，不新增词表 unit。

与既有约定的衔接：

- 前置事件识别不等于整条款的完整提取。后续仍须按条款提全全部规定，并复用已经建立的事件；“每条款恰提取一次”指后续完整提取的任务职责，不能仅因已有事件记录就将条款登记为完成。
- 各 unit 的具体提取调度留到设计阶段；本项不一并确定全部定义值等其他共同信息的前置建模。
- 事件识别、引用与前置顺序已经确定。事件漏提经后续讨论归入一般提取质量风险，不再作为独立待决问题，见 §1.7；ID 格式、命名、锚和参与者结构属于具体设计事项。

### 1.7 事件漏提风险与入库 skill 总体工作流收口（2026-09-25 用户裁决）

裁决内容：

- **事件认定由负责事件提取的 sub-agent 统一承担**，包括识别事项、确定粒度及判断是否同一事件；各 unit 的关系提取 agent 使用已有事件记录与 ID 建模，不承担重新认定事件的职责。
- **事件漏提归入一般提取质量风险，不再作为事件机制的独立待决问题**。遗漏可能影响条件或时间基准的准确表达，条款覆盖检查也不能证明事件已提全；这属于既有断言级完整性的边界。当前接受该风险，不为其增加专门检查或补提流程；后续若实际验收暴露出明显问题，再据具体表现讨论调整。
- **入库 skill 的总体工作流收口**。沿用此前已确认的步骤与分工，完整顺序如下：

| 顺序 | 环节 | 执行分工与产物 |
|---|---|---|
| 1 | 开工 | 主会话调用案件 CLI，加载并冻结词表快照，记录案件出身 |
| 2 | 预处理与登记 | 调用预处理 CLI，登记各份素材及不可变的文本版本；转换异常按既有规则处理 |
| 3 | 切条款 | 脚本按原文结构切分，保存条款地址与文本，验证字符覆盖，记录切分异常 |
| 4 | 通读准备 | sub-agent 通读全部素材，生成案件概要；负责事件提取的 sub-agent 识别事件及其所需主体，产出带出处的记录文件 |
| 5 | 写入事件 | 主会话按 §1.5 调用 CLI 校验、写入，形成供后续提取引用的案内事件 ID |
| 6 | 打标与分组 | sub-agent 并行逐条款打 unit 标签，脚本按标签逐字导出分组文件 |
| 7 | 关系提取 | 各 unit 的 agent 取得案件概要、共用事件记录、负责条款和词表，完整提取条款内容，产出完整 JSON 文件及条款清单、摘要 |
| 8 | 提交提取结果 | 主会话逐文件调用一次 CLI；成功登记完成，失败交回原 agent 修正后重试 |
| 9 | 对账 | 主会话调用 CLI 执行既有机械六查，取得指向具体记录的报告；修正遵循既有命令与追加式存储约定 |

职责与边界：

- 大量阅读由 sub-agent 承担，主会话负责编排、提交和结果处理。概要提供共同背景，事件记录提供正式引用；各 agent 不因串行运行而自动获得其他 agent 的输出。
- 分组用于组织阅读上下文，每条款仍完整提取一次；前置事件识别不把整条款登记为提取完成。
- 缺口聚合由词表治理流程承接，按 §1.9 低频、按需开展，不是每份合同入库后必须等待的一步。新素材到达仍沿用登记、切条款、通读准备、打标分组与提取的既有路径。
- 本次收口确定总体步骤、依赖与职责。字段、ID、JSON、CLI 参数、具体调度及一般纠错的实现细则进入设计阶段，见 §2.2；本次不另行裁定各 unit 提取一律串行或并行。后续涉及新增或修改流程、机制、命令的事项，仍须先经用户决策。

### 1.8 初始化 skill 的人工审定通过文件意见交接（2026-09-25 用户裁决）

裁决内容：

- **提取、整理出的结果写入文件，人工直接在该文件中写意见，agent 再读取并按意见整理结果**。意见用自然语言表达即可，不要求专门的意见格式或审批机制。
- 两道人工审定均采用这一方式：第一道审定候选单元，agent 按意见整理定稿单元表，供第二遍提取使用；第二道审定槽的提取结果，agent 按意见整理词表产物，继续既有收尾与输出步骤。
- “两遍两闸”的总体顺序沿用 principles.md §8.1，人工交接问题据此收口。正式词表的写入继续遵守既有词表工具约定；文件格式与具体工具调用进入详细设计，无需为意见交接另建精密流程。

### 1.9 词表治理采用低频、按需的简单流程（2026-09-25 用户裁决）

裁决内容：

- **结合案件缺口汇总与律师主动提出变更两种入口**。词表治理低频发生，按需发起，无需精密的流程设计。
- 共用处理顺序：**案件缺口汇总或律师要求 → agent 对照当前全局词表及相关证据，整理具体建议文件 → 人工直接在文件中写意见 → agent 按意见整理变更内容，由主会话调用词表 CLI 执行 → 输出变更摘要**。涉及大量条款阅读时沿用 sub-agent 读手原则；人工交接沿用 §1.8 的自然语言文件意见。
- 对缺口汇总先判断当前词表是否已经能够表达，再决定是否建议新增或整理条目；律师主动提出的要求也结合现有词表形成具体建议。报告中的建议附理由及相应证据，不把旧案件的缺口直接当作当前词表仍有缺口。
- 词表仍在全局由律师决定、经工具增删，修改通过新增条目并删除旧条目表达；旧案件快照保持冻结。原“删除只发生在全局聚合那一步”相应改为“删除发生在全局治理中”，律师主动发起也可进入同一处理流程。
- **词表治理 skill 的总体工作流据此收口**。初始化继续采用“两遍两闸”，后续治理采用本项的简单流程；文件格式、CLI 参数等进入详细设计。

### 1.10 当事人性质沿用八种核心值与原文功能标签（2026-09-25 用户裁决）

- 关系中的核心性质沿用义务人/受领人、行使方/承受方、享有方/相对方、受保护方/受限方八种。
- 解除核心性质与模态字段的强制绑定，模态可空；功能标签仍按原文填写。
- 不按语法主语强制确定关系端点；当事人之间的关系仍遵循二元表示。此项不重新建立情态词机械验证。

### 1.11 同一 JSON 文件整份成功或整份不写入（2026-09-25 用户裁决）

- 一份 agent 结果文件中，任一记录未通过校验，整份都不写入。
- 返回具体错误，由原 agent 修正后整份重提；同一文件不采用部分成功、部分重提的处理方式。
- 成功文件的重复提交行为由 §1.12 确定。

### 1.12 成功文件重复提交返回已有结果（2026-09-25 用户裁决）

- 同一份已经成功写入的结果再次提交，返回第一次的写入结果，不新增重复记录。
- 内容有改动的文件另作新提交；涉及已入库内容的纠正，仍遵守追加式修正规则。

### 1.13 词表使用 JSON 写法，保持零第三方依赖（2026-09-25 用户裁决）

- 全局词表采用 JSON 写法保存；该写法属于合法 YAML，使用标准库解析和输出。
- 不支持 YAML 注释、缩进映射等额外语法，不引入 YAML 解析库。
- 人工意见仍写在可读的审阅文件中，由 agent 理解后通过词表工具落实。

### 1.14 原始材料随 SQLite 案件库保存（2026-09-25 用户裁决）

- 原始 PDF、Word 等文件的字节也存入 SQLite，随单个案件文件完整交付。
- 转换后的全文继续入库，原始文件与转换文本分别保存、分别计算哈希；原路径仅作来源提示。

### 1.15 肯定与否定通过现有槽和值结构表达（2026-09-25 用户裁决）
