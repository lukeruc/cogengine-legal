## 4. 切分规格缺陷与已复现的实现缺陷

### 4.0 按空行切出的片段被当作条款，分组没有恢复条款归属

**条款切分及下游组织未通过核心功能验收，优先整改。** 用户从运行日志指出：合同只有几十条，却切出上千片。数量差异是检查线索；由于合同可含子条款、附表、前言，不能单凭数量认定错误。本次进一步核对了实际片段内容、切分代码和后续分组行为，确认原合同的条款组织没有被完整保留。

当前库中 1537 个 clause 对象只有 32 个 original_number 非空，其余 1505 个为空。这个数字不代表合同只有 32 条，也不代表其余全是错误；具体问题可见以下同一节内的连续片段：

| 片段 sequence | 当前保存的内容 |
|---|---|
| 1002 | `## Rate of Progress` 标题，归类为 no_content |
| 1003 | 单独的引导语 `If, at any time:` |
| 1004 | 条件 (a)，句尾为 and/or |
| 1005 | 条件 (b)，句尾逗号 |
| 1006 | 对条件的排除情形，以及随后雇主可发出指示的权利 |
| 1007 | 承包商采取措施及承担费用的后续规定 |

相邻的 `Delays Caused by Authorities` 同样被拆成标题、if 引导语、三个条件和 then 后果，共六片。证据及完整选定片段见 [clause-structure-review.json](../work/acceptance-review-2026-09-28/clause-structure-review.json)。

原因与后续影响：

1. [splitter.py:43](../src/legal/splitter.py#L43) 无条件将空行后的非空行加入边界；条款内换段也会产生新 clause。条款标题、条件列举和法律后果由此成为独立记录。
2. 当前字段保留位置顺序，但没有保存这些片段共同所属的完整条款及其范围。[group.py:38](../src/legal/group.py#L38) 仅按各片段的标签分桶，不按原条款重新组织完整内容。上例标题进入 no_content 组，正文片段标签也不完全一致；有些组因标签相同仍可同时取得若干相邻片段，但不能据此认为条款组织已经恢复。
3. 打标、负责条款清单和完成统计均使用这些片段 ID。因此“每条款完整提取一次”的机械完成事实，实际只能证明片段被处理；条件、例外及后果的共同适用范围仍依赖读手重新拼接理解。它增加了错误分配阅读上下文和遗漏条件的风险，本项未声称每个被切开的条款都已出现语义错误。
4. **代码此处遵循了 spec §12.3 第 3 项**：该项明确要求每个空行分隔段落起点成为边界，并承认不保证片段是独立法律条款。principles 要求按合同结构切条款，后续流程又按完整条款安排责任；规格没有落实两者之间的完整归属。因此不能只归责实现偏离 spec，规格本身也需修正。

上一轮验收把字符守恒、固定切分样例通过列为已验证事实，这些事实仍成立；但没有充分核验它们是否实现了“按条款组织”，属于验收遗漏。修正方向应先明确原条款、子条款及其正文归属的验收要求，确保条件、例外和后果具有完整的阅读范围；不能仅把目标改成减少片段数。具体机制及规格变更须由用户裁决，本次只补充验收结论。

第 5 节的 35,550 美元截止条件在原片段 1011 内实际完整存在，不能仅据本项就将那处提取遗漏归因于切分。

### contract_v3 原版与本项目适配的对照核验

用户指出原版 contract_v3 的分段处理已有成功实践，本次整改应以其完整的条款组织链路作为复用基线。本轮直接检查了用户指定源码，得到以下证据：

| 对照项 | contract_v3 原版 | 本项目当前实现 |
|---|---|---|
| 扫描结果 | scan_structure 保存条款起止行及章节归属；_finalize_line_ends 将正文范围延续到下一条款前 | scan_structure_reference 的识别逻辑基本原样保留，只适配字符串输入和文件名 |
| 后续组织 | render_structure 建立标题层级；split_topics 按三级条款标题及其正文分组，四级及更深正文随所属条款保留 | splitter 额外加入每个空行后的段落起点；group 随后按片段标签收集 |
| 空行作用 | 可分隔正文段落，条款归属继续保留 | 直接生成新 clause |
| 原文保存 | 渲染阶段会清理标记、拼接换行 | 本项目需要保持登记文本逐字不变，复用时应取结构边界及归属，保留精确原文切片 |

原版 scanner 的 SHA-256 仍为 spec 固定的 `d48b432865dcc66fb3693dc07b6b12b364b8d558c9d01dde317ff085c1cb16b3`。文件对比显示，当前 scanner 副本只改了入参和输出文件名，**把段落变成条款的直接改动发生在新增的 splitter 适配层及其规格要求中**。

用“两条中文条款，第一条包含付款正文及另起一段的例外，第二条包含交付正文”的最小输入实际对比：

- 原版 scan → render → split_topics.parse_clauses：得到 **2 个完整条款**，付款正文及例外在同一条款内。
- 当前 split_text：得到 **5 个片段**，两个标题、付款正文、例外和交付正文分别成片。

上述对比是在同一输入上执行得到；输入、完整结果及原版三个脚本哈希见 [contract-v3-structure-comparison.json](../work/acceptance-review-2026-09-28/contract-v3-structure-comparison.json)。

**还须处理本合同的输入结构问题。** 既有 [源件审计](../work/case-onshore-2025-01-08/source-audit.md) 已报告 Word 自动编号未进入 Markdown，以及 26 处交叉引用误切。本轮补充独立确认：

- DOCX 的 General Provisions、Definitions、Rate of Progress、Delay Damages、Arbitration 标题确有 Word 自动编号属性及层级；登记 Markdown 的对应标题没有显示编号。
- 片段 334 的定义止于 “certificate issued under”，335 从正文交叉引用 “Clause 11.9” 开始；388/389 也把一句定义中的 Schedule XX 引用切开。它们不能据此变成新条款标题。
- 将原版 scanner 直接运行在此次原始 Markdown 上，得到 **0 个章、30 个 article 候选**。这不是完整合同条款清单，也不是对用户此前成功的 contract_v3 全流程运行的复跑。

因此，整改必须复用“识别结构—保留完整条款—按条款组织阅读”的行为，并核对当前转换输入。只删除空行切分规则或只替换 scanner 文件，都不足以宣告本合同的条款切分已修复。不能未经证据把自动编号丢失、交叉引用误识别全部归因于新增适配代码；这两项是本次输入和现有识别边界共同暴露的问题。

### 4.1 合法的“以锚为前提”推断无法完整提取，查询出处为空

**优先修复。** spec §4.2 明确允许来源 III 的前提直接为 anchor。最小案件中，以已存在的合法锚作为 relation 的推断前提：

1. 用 correction 写入成功，但查询该关系时 `provenance[].anchors=[]`。
2. 将相同关系作为该条款的 extraction 内容提交，工具报 `COVERAGE_INVALID: no modeled content in this submission`，整份拒绝。

原因是 [query.py:79](../src/legal/query.py#L79) 的出处递归和 [model.py:615](../src/legal/model.py#L615) 的覆盖递归均只读取 assertion_sources；anchor 本身按规格没有 assertion_sources，因此到达锚后得到空结果。来源合法性校验的 roots 已认可 anchor，后续两条路径却未承接它。

影响：已批准的来源 III 能力在合法输入下被阻断；已写入的记录不能通过标准出处展开取得原文根链。不是要求系统判断推断语义正确性，而是要求其保留已合法提供的依据。

复现：测试 `test_08`、`test_09`；依据 spec §4.2、§8.2、§9.3，关联 A22。现有真实案件的来源统计只有 I 级 6314 条、II 级 7 条，没有 III 级，原成功案例未触达这个分支。

### 4.2 关系修订后，当前查询丢失对应历史缺口

**优先修复。** 先为关系 R 的第 1 版建立 missing_slot 缺口，按裁决固定 related_object 到该版本；再为 R 追加第 2 版。修订前查询 R 能看到该缺口，修订后 `gaps=[]`。

缺口仍存在数据库中，也能通过旧版本或独立缺口查询找到；问题是**当前关系的查询不再提示这一历史缺口及目标已变化**。这与缺口自动解决不同，程序没有任何依据将其从关联结果中隐藏。

原因：[query.py:193](../src/legal/query.py#L193) 的 `_gaps` 用 `related == row.record_id` 匹配，没有通过固定记录解析稳定 object_id 后匹配，再展示 changed/withdrawn。

复现：`test_10`。依据 decisions §1.27、spec §9.3、A30。

### 4.3 按归一后的主体筛选，漏掉已存在的细节

**优先修复。** 已有甲→乙的付款关系及金额细节，将甲通过合法 redirect 指向另一主体节点。按该归一目标进行 `--kind detail --party <目标主体>` 查询，返回 `total=0/no_record`，但该细节仍存在并挂在该付款关系下。

原因：[query.py:451](../src/legal/query.py#L451) 的 detail 分支只比较 owner 的原始端点 ID；relation 分支却会查询归一终点。两种记录过滤口径不一致。

影响：消费者按整理后的主体读取义务细节会得到错误的无匹配结果。复现：`test_11`。依据 spec §9.3 关于“原始主体及无冲突归一终点，detail 随 owner”的约定。

### 4.4 没有拒绝不支持的案件格式版本

模拟由未来版本程序产生的案件头，分别令 schema_version、value_format_version、code_version、vocabulary_format_version 为 999，当前程序仍成功读取并返回词表，而不是 UNSUPPORTED_VERSION。

测试仅重建临时夹具的 case_info 表以模拟未来数据库；没有绕过生产写接口修改送验原库。当前版本自己的建库 CHECK 约束不能替代读取其他版本数据库时的版本检查。

原因：[storage.py:25](../src/legal/storage.py#L25) 的 CaseStore 只确认 case_info 存在，未核对版本。复现：`test_12` 的四个子测试。依据 spec §1.2。继续静默按版本 1 解释其他版本数据，会使格式演进后的读取失去明确边界。

### 4.5 reconcile 未落实规格要求的存量结构复核

在已通过对账的临时小案件中，把持久化金额的单位改成未配置的 `UNKNOWN`，同时更新记录 JSON 和细节表的值，随后 reconcile 仍返回 `passed=true`。

**这是受控的存储故障注入，未发现送验真实案件已经含有这种未知单位，也未声称正常 write 会接受它。** 正常 write 在另一用例中确实拒绝了未知单位。本项证明的是：spec §11.1 要求对账复核存量的结构、引用、槽结构和版本链，目前未充分实现，不能用对账通过替代这些校验。

[reconcile.py:92](../src/legal/reconcile.py#L92) 对值主要检查 II 级往返、对来源主要检查是否至少存在一行，没有对全部存量值再次验证合法结构。复现：`test_14`。修复应沿用已定六查的归类口径，不因此新增核对员或新工作流。

### 4.6 非法锚出现序号被静默改成 1

分别提交 `occurrence:0`、`false`、`null`，均写入成功，并被当作第 1 次出现。规格要求提供时为正整数，只有字段缺席才能使用默认值。

原因：[model.py:269](../src/legal/model.py#L269) 在类型/范围检查前执行 `occurrence = occurrence or 1`，把非法值与缺席混同。

影响：调用方显式给出的非法定位没有被拒绝；有重复引文时这种处理还可能错误选择第一处。复现：`test_13`；依据 spec §2.1、§3.4、§4.2。

## 12. 再验收的明确断言

### 12.1 条款切分与分组

| 输入/场景 | 验收断言 |
|---|---|
| 两条中文条款、条款内多段正文与例外 | 与已保存原版对照样例相同，得到 2 个完整分析条款；例外与主规则共同可读 |
| 本案 Rate of Progress | 标题、if、(a)/(b)、排除条件、雇主权利和后续义务在规定的完整阅读范围内；不再把 if 单句分配为独立完整提取职责 |
| 本案 Delays Caused by Authorities | 三项共同条件和 then 后果保持同属一条规定的上下文 |
| 本案 Delay Damages 表格 | 两台机组、全部表头和费率行、共同上限及表后例外具有正确条款归属 |
| 正文软换行后的 Clause / Schedule 引用 | 不产生新条款边界，不把引用号填为当前条款编号；覆盖片段 334/335、388/389 的原句 |
| Word 自动编号及重启 | 抽定真实标题的编号、层级与原件一致；不能只验证文本哈希或目录字符串匹配 |
| 重复编号、无编号正文、附件、前言和签署页 | 全文保留，地址唯一，各区域归属或不确定性明确；普通续段不因无编号自动变成独立条款 |
| CRLF、空白和多字节字符 | 基础区间逐字覆盖，无空洞、无重叠、无偏移单位错误；所有锚仍可回到登记文本 |
| 一条款带多个 unit 标签 | 每个相关组得到同一份完整原文；完整提取职责仅分配一次 |
| 批次及任务边界 | 负责条款集合两两不交且覆盖本轮范围；不能把条款内部条件分派到另一个独立职责中 |

还应从用户认可的 contract_v3 成功案例中固定至少一份输入、结构结果和分组结果作为对照样本。当前仅完成原版源码及最小样例对比，尚未取得并重放其此前成功案例的全套产物。

以上属于实施完成后的测试和验收证据，不把人工逐份确认结构变成每次正常入库的新步骤。
