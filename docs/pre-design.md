2026-09-09

**起因：调查 Accord Project**

为"合同结构化工具"找参照系，调查了 Accord Project（Linux Foundation 旗下开源智能法律合同技术栈，2017 起，68 仓库）。要点：

- 模板三要素（Text/Model/Logic 同源一体）证明"结构化与文本可互指"可行
- Concerto 是封闭世界 schema 语言；它的 .voc 词表只是模型的本地化标注层，无结构权力。可借的模式：concerto compare 的语义 diff（模型版本间破坏性变更分级）、格式契约、多语言实现一致性测试
- Cicero 解析 = 模板即文法（静态文本=终结符、变量=非终结符、Earley 解析），`render(parse(text))==text` 恒等式是完备性检验的范式。但只对"由模板生成的合同"有效，对任意合同是死路
- 任意文本分类（labs-cicero-classify，BERT NER）停在原型未产品化——诚实承认无模板场景结构化无机械解，只能 LLM 提取 + 机器验证
- 工程教训：区块链集成一代全部归档，活下来的是 Concerto 本体语言和 models 仓库——底座的长寿资产是本体与代数，不是管道与集成

**需求澄清**

- 要做的是真正的结构化：不是条款序号→内容的 key-value，而是合同实质（金额、付款条件、交货方式、交货时间）入库为字段，且字段能链接回原文
- 三个未解难题：字段本体从哪来；值不是标量（付款条件是嵌套结构、交货时间是相对事件）；怎么保证提得准（答案=LLM 抽取+机器验锚，冲突并存即风险点）

**两层机制（用户提出）**

第一层是商业交易的基本行为单元（认知单元），第二层是该单元下可设立的细粒度规则。

**目的讨论**

- 两个不变量：完备性（无漏项：读库可读全部合同信息）、忠实性（无添加：库里没有文本之外的东西）
- 语义完备性不可机械判定 → 重述为"无未处置状态"：每段文本要么结构化、要么显式判定无需（带人和理由）、要么在池里。完备性从布尔值变账面透明的状态机
- 配套讨论：原文整篇入库存放（零解释）+ 带锚的结构记录；机械审计（字符覆盖 / 值枚举 diff）；无添加分三级（原文引述 / 机械变换带格式契约 / 显式推断），永不混层
- 目的候选（审核底座 / 数字资产 / 数字孪生 / 履约基建）分岔后钉死：

**定位钉死（用户裁决）**

> 基础设施性质的底座，只关注一件事：对商业世界的法律关系做精细化建模。

- 排除：抽取体验、审核逻辑、UI/签署/CLM 都是下游租户
- 边界：本项目只管"合同文本规定了什么"，不管"世界里实际发生了什么"；判断违约要把实际发生的事实对照合同规定，那是消费方的工作，需要两份输入
- 由此收回此前"需求驱动 schema"的建议——那是应用层思维；底座按法律关系本来的样子建模，查询方适配本体
- 资产排序：本体 > 代数（查询/diff/切片/合并）> 实例账本 > 抽取管道（最短命，随时换）
- 第零条判定法：凡是只在"读模型的人"那里才存在的问题，都不是建模层的问题
- 验收测试（提案）：三份既有规则文件的每条检查项都必须能表达为模型上的查询

**两个假问题（用户否定，理由留痕）**

- 合同群：建模对象是带锚的关系，文档只是锚的靶子；合同群=同图多素材，零新增机制；唯一新增工程量是跨文本节点同一性
- 法域：上层按商业世界的认识分类，法域差异只落基层词表扩展。更深理由：模型是描述性的，法域是评价性的=消费者问题。实证：三份规则文件（中国法×2 + FIDIC）主题结构平行
- 强加治理义务：基层词表必须走"池→认定→晋升全局"集中通道，防方言化（前车之鉴：Concerto namespace 泛滥）

**两次抢跑被纠正（留痕）**

- 写设计文档被叫停：当时还没讨论清楚目的
- 直接定义基础概念（义务/事件/条件）被叫停：那是词表内容工作的开头，是律师的事；系统工作是为两层机制先做形制设计图。原子结构（义务边 vs 单元聚合）挂为待决

**命名（定稿）**

- 整体：两层词表（代码 lexicon）
- 第一层：交易单元（unit）——取自"商业交易中的基本行为单元"，加"交易"避开规则-builder 的"判断单元"
- 第二层：规定槽（slot）——三条理由：①命名的是可设立的可能性而非实际设立（值在账本），名字本身教结构；②可缺性原生（槽空着=合法状态且是审核信息）；③FrameNet 学术血统
- 避开撞名：规则（检查项占用）、主题（消费者侧粗分组）、条款（原文层的文本单位）、框架（框架合同）、裸"单元"（判断单元）
- 分界一句话：词表管单元和槽，账本管值

**框架语义学细说**

- 槽的双重血统：Minsky（1974，AI，frame/slot/filler，槽字面来源）+ Fillmore（1975-82，语言学，框架语义学→FrameNet 1997-，FE 概念来源）。本项目=用 Minsky 的可填可空槽形制，装 Fillmore 的场景角色语义
- Fillmore 核心思想：词义相对背景场景定义，理解词=调用场景结构（buy/sell/pay/cost 是同一商业交易场景的不同透视；land vs ground 不同框架）。"上层分类依据是商业世界的认识"正是 Fillmore 立场的合同版
- FrameNet 工程：英文约千余框架、1.3 万词元、20 余万人工标注句；多语种含中文 CFN——多语可复制性支持"法域/语言中立的上层"论断。构件：Frame / FE（核心 vs 周边）/ LU（触发词）/ 标注（文本跨度打角色标签）
- FrameNet 的标注实践就是"锚"的实践（span 指回原文+双人一致性）；本项目把人工纪律换成机验纪律
- 对照可抄：核心 FE/周边 FE ↔ 核心槽/周边槽（核心槽缺席=单元身份存疑；周边槽跨单元复用：时点/地点/方式/除外）；LU ↔ 识别特征；Perspective_on ↔ 立场（Commerce_buy/sell 同一场景两透视 ↔ 买方/卖方规则文件）；Subframe+Precedes ↔ 交易时序骨架；Inheritance ↔ 单元特化（子框架 FE 须与父一致）
- FrameNet 没有的（本项目增量）：道义结构（义务/权利/条件/但书/救济是 Hohfeld 与道义逻辑地盘）、类型化值与表层契约、治理管道、账本纪律。定位公式：框架语义骨架 + 法学道义层 + 账本纪律
- Fillmore & Atkins 1992 risk 研究范式：两万例句逐例归纳场景——单元识别特征应从真实合同语料逐例阅读（KWIC）中长出，非闭门起草；律师拍板但作业方式=归纳

**schema 设计的两条血脉（回答"这些学科是不是现代 schema 设计的指导"）**

- 不是"很多"，是一条特定传统：工程传统（Codd→Chen ER→DDD→JSON Schema，管数据完整性/互操作，大多数 schema 实践在此）vs 意义建模传统（Minsky+Fillmore→KL-ONE/描述逻辑→OWL/本体工程；FrameNet→SRL/标注体系/槽填充，管对自然文本语义建模）
- 本项目在意义建模传统主场。该传统活水：FrameNet→语义角色标注；Minsky→描述逻辑→W3C 本体栈（FIBO/schema.org）；Hohfeld/道义逻辑→LegalRuleML/Akoma Ntoso
- 学术生态位：FIBO 偏金融工具、UBL 偏单证流转、FpML 偏衍生品——商业合同实质建模是空档。单元层动手前应对这三个做 due diligence（Accord models 仓库有 FpML 转录入口）
- 趋势：LLM 结构化输出使两传统合流（schema as cognition constraint），项目时机踩在合流点上

**第一性原理重推三层结构（用户提出，讨论验证）**

描述法律关系 = R(主体a, 主体b; 类T; 细节{槽:值})，至少三层：

- 第一层 主体对（谁与谁——无此=抽象知识非关系）；第二层 关系类（什么性质——无此=不可解释）；第三层 类中细节（如何具体——无此=同对主体同类关系不可区分，如分批交付）。“至少”成立
- 与词表/账本咬合的表述：词表=抽掉第一层的三层结构（无主体的类+槽形制）；账本=补上第一层的实例。第三层内部再切：槽形制（词表、律师领域）与槽值（账本、带锚）——即既定的"词表管单元和槽，账本管值"
- 收敛证据：属性图带属性边 / RDF 再化——独立推导落到同一形状
- 压力测试四个裁决：
  1. 第一层自带方向与角色：Hohfeld 对偶——存一条边两面读（A→B 付款义务 = B→A 收款权利）；角色是边属性、实体是节点
  2. 二元为原语：多方（连带）降解为多条二元边+协调规定
  3. 道义模态落位【新待决】：单元自带模态（付款=义务类、解除权=权力类）vs 类×模态正交双维——倾向前者，待裁决
  4. 时间与条件不是第四层：约定期限/条件/生效=第三层槽；合同当前处于什么状态（已生效/已终止）是"文本规定×实际发生了什么"的对照结果，属查询层，符合不裁决铁律
- 第四维：锚（依据）是忠实性不变量强加的正交必备维——每层主张指回文本跨度
- 图需两类非关系支撑节点：事件（条件/时点指针对象）、定义事实（单主体记录）

**师承结论**

- 判断"主要向语言学学"对一半：语言学的理论内核为陈述性语言而建，合同是规定性语言——规范语义的主师是道义逻辑（von Wright / Alchourrón-Bulygin）与法教义学（Hohfeld）；但语言学的工艺层是本项目日常主师
- 四门手艺：框架语义学（场景-角色、核心/周边、框架关系→单元层形制）；词典学（义项切分、边界情形、用法注记→词表条目作业范式）；语料库语言学（KWIC 逐例阅读、标注一致性→识别特征建法+抽取质量机验）；术语学（Wüster 传统、ISO 704、TBX→词表晋升治理规程不必发明，抄术语协调）
- 师承表：形制设计→FrameNet+本体工程（副：术语学）；词表内容→词典学+语料库归纳（副：律师裁决）；规范层→Hohfeld+道义逻辑（副：法教义学）；阅读工序→标注学（副：信息抽取工程）
- 一句话：向语言学学工艺（编词表/读语料/治术语），向法学与逻辑学学规范结构

2026-09-10

**清空重推：建模文件到底是什么**

- 从目的单独重推（不带此前结论）。被建模对象三个本性：是解释的产物（不是文本本身）、有时间生命（随补充协议生灭）、权威永远在文本
- 先推成"带锚的解释主张账本"——被用户纠正：某一时刻的法律关系就是一个静态事实，不需要靠主张史才能存在；"过程贵"不等于"成品要保留过程痕迹"
- 修正后定性：文件是**带时间范围、带锚、带认知状态的静态事实库**。每条事实四要素：内容（主体对/类/细节）、锚（存在许可，指回原文）、认知状态（提议/认定，并存的字段而非历史）、有效范围（锚定哪个文本版本/什么时间区间）。演化=新事实带新范围，不是改写旧事实
- 此刻的关系图=按时间取切片（查询模式）；合同改版=新版本进来、事实重新限定范围（重锚定问题在此出现）
- "账本"从文件本性降级为实现选择：逻辑上是状态；物理上可选追加式存储+折叠（白得修正审计与库层禁改写纪律）或可变状态库（更简单），工程权衡非第一性原理结论

**全部重来：权利义务关系怎么存**

- 解剖一句话（"卖方须在收到预付款后30日内向买方交付设备，迟交超4周买方有权解除并按总价10%索赔"）得原子：谁对谁、什么性质、关于什么事、具体怎么定
- "类"拆成两个字段：**性质（模态：义务/权力/许可/豁免——封闭小表，写死在程序里）× 行为类（付款/交付/保密/竞业……开放词表，律师治理）**。两表变化速率、治理、规模完全不同。（解决了此前"道义模态落位"待决）
- 事件是连接铰链：条件、相对时点、触发都指向事件；事件常是另一关系的履行（"收到预付款"=预付款义务的履行），关系与事件互相引用是一等结构
- 救济不需要专门机制：违约金、解除权就是"被违约事件触发的二级关系"，与基础关系同形状。合同=一堆基础关系+一套事件触发的后果
- 细节值五种形态（封闭，写死程序）：量、时（绝对日期/相对事件/期限）、条件（复合）、除外（但书）、算式。复杂值由五种拼装（如付款安排=重复组）
- 存储五件套：关系表（负担方/受益方/模态/行为类/状态/有效范围）、细节表（关系id/细节名/值/值形态/锚）、节点表（主体/事件/定义值）、引用表（条件、触发、算式指向）、锚表
- 词表由此分三种：模态（封闭）、值形态（封闭）、行为类+细节条目（开放，唯一需要治理管道的）

**RDF 与 Neo4j（背景澄清）**

- RDF=把一切知识写成"主语-谓语-宾语"三段式小句子的 W3C 格式标准；箭头本身不能带属性，挂细节要"再化"（把关系变成节点再围着写），对我们场景别扭
- Neo4j=图数据库软件（图版 MySQL），属性图模型箭头自带属性，天然友好；但是要安装起服务的重型依赖
- 结论：五件套=用 SQLite 手搓属性图——模型上借属性图思想，工程上零依赖单文件，两个现成方案都不用

**技术选型定案**

- CLI 工具 + 编辑一个 SQLite 文件。一命令一进程干完即退；一文件一事项，文件即案件，拷贝即迁移；零依赖纯标准库，无服务器

**词表存放：案件为源、全局为聚合派生**

- 否掉"全局主库、各案引用"（案件不自含；词表演进会悄悄改变旧案含义；全局文件单点故障）和"各案副本+定期同步"（常驻同步义务；方言化温床）
- 定案四条规矩：①开工时把全局词表完整拷进案件文件当快照（KB 级整拷，案件从此自含，放多少年自己解释自己）②办案中新词经认定写入本案词表（只增）③定期聚合命令扫全部案件产出对比报告（新词晋升/用法不一/建议废止），律师过目后才更新全局 ④全局词条只标废止……（此条后被修正，见下）
- 更新哲学：不畏惧"增"——快照隔离+槽可空托底，漏一个字段零代价（进池等认定），预先穷举才是浪费；初始词表起点尽薄、从真实语料归纳着长

**用户修正：不能改，只能增删**

- 条目不可变：一个词条 id 的含义永远只有一份，解释永不漂移，不存在"哪一版的它"
- 想"改"=增新条目+删旧条目；取代关系本身是显式事实（新条目可带可选字段"取代了谁"，供跨案统计对齐两代概念）
- 删是安全的，因为旧案快照在手；"永不删除只废止"的重规矩不再需要
- 分工：案内只增（删不需要）；删只发生在全局聚合那一步、有人把关
- 胆量来自架构（快照+可空），纪律来自通道（池→认定→晋升唯一入口，律师确认才生效）

**词表是外置"变量"文件，工具不含内容**

- CLI 不蕴含开放词表，程序只带规矩（模态、值形态两张封闭表）；词表是外置数据文件，须先加载，没有它工具空转
- 好处：换行业换律所，工具一字不动换一份变量文件；无预置词表逼着内容从语料归纳来
- 命令面：词表 初始化/列/查/增/删/diff；开工 --词表 xxx（加载并拷快照）；聚合（各案→报告→律师过目→词表增删）
- 开工时记录加载源（文件名+内容哈希）作案件出身，旧案永远能回答"我出生时用的哪份词表"
- 工具是变量文件的唯一正门写入口：校验值形态拼法、引用完整性，绕过工具的手改由加载时校验+git diff 显形

**CLI 分两部分**

- 变量组（只对词表文件动手）与案件组（只对案件 .db 动手），互不越界
- 两条桥：开工（词表→案件，向下拷快照）、聚合（案件→报告→词表，向上回流经验）；除桥外无命令同时碰两种文件
- 案件组也会动词表，但只动案内私有快照、只增不删
- 两分对应两种节奏：变量组=治理工作台（慢、人审）；案件组=日常流水（快、机器重活人拍板）。将来变量组可独立成交互工具，接口就是词表文件

**变量组完整体现二级词表**

- 词表文件存三种东西：单元条目（名/别名/识别说明/取代了谁）、槽条目（名/值形态拼装/取代了谁）、归属关系（槽↔单元，多对多）
- 通用槽池：完全不挂归属的槽（时点/地点/方式/但书）任何单元可用——FrameNet 核心/周边的落地：周边共享、核心专属
- 值形态用五种基本件拼装，工具按代码内语法校验拼法，拼不合法拒写
- 删单元不株连槽：多归属的槽留下，谁都不挂的自动降为通用池；两级各有生死
- 命令分层：词表 增 单元 / 增 槽（--归属）、列 --单元（看一层）/ --槽（反查归属）

**变量文件格式选型（定案：YAML）**

- 文件性质：小（KB 级）、慢变、律师长期资产、变动要人审、要历史追责、要可移植——治理需求决定选型，性能无关
- SQLite 唯一优势"难手改"是弱保护；真门卫=加载时严格校验（不合语法/引用悬空拒绝加载）+git diff 显形手改
- 文本胜在：人审（改动即 PR，律师逐行看懂）、历史（git 全套：blame/回滚，不必自造版本机制）、协作（文本可合并，二进制锁死单人）、长寿（纯文本是存活最久的格式，词表生命周期以十年计）
- 定案：**文本为源、SQLite 为运行快照**。源=git 仓库里的 YAML 目录（每单元一文件+通用槽一文件；起步可单文件，规模永远不用强制拆）；开工时读→校验→算内容哈希→写进案件 .db 当快照；哈希入案件作版本戳。经典"源码与编译产物"关系

**初始词表怎么来（不是手敲）**

- 初始版本=机器起草、律师过目的一次批量认定，即日常零散"池→认定"的出生批次
- 第一次提案（从三份规则文件派生）被用户纠正：规则文件是特定合同种类的需求快照，主题是消费者侧粗分组，当原料会带种类偏。它的角色就是考卷（验收测试），不是原料
- 单元的抽象只能从跨种类重复中来：一个行为在多个合同种类里作为主题出现才有单元资格
- 法律文本（民法典合同编通则/CISG/UNIDROIT 通则）从"骨架"降为"查漏清单"：法条给的是规制类别，按"法律怎么管"切块≠按"当事人在干什么"切块；只用于事后发现漏读的条款类型，不从法条造单元

**语料归纳的 agent 任务（初稿，后被两遍两闸工序取代）**

- 形状：编排者派读手、读手各读各的、中心聚类；读手锁死输出格式、只报告不发明（防提前聚类导致不可合并）；两阶段防锚定（先自由抽取、中心聚类、再回头重标注找残留）
- 读手不需要懂词表概念——单元资格含跨种类检验，单份合同的读手不可能判定，边界裁决只能归中心

**unit 与 slot 的区分判据**

- 一句话判据：**单元是关系本身的名字，槽是关系的属性**。检验："谁对谁有一个X"问得出口是单元（交付、预付款、保函、保密撑得起谁对谁骨架）；问不出口、只能依附的是槽（说不出"谁对谁有一个比例"，只有"付款的比例"）
- 单元三资格：主题检验（存在以它为主题的条款）、关系检验（谁对谁）、跨种类检验（多个种类中作为主题出现）。槽两资格：依附检验（离开单元无意义）、参数检验（限定安排而非构成安排）
- 灰区判例：质保期常做条款标题，但"谁对谁有一个质保期"问不出口→槽（质量担保的时长参数）。条款标题≠单元

**粒度之争与吸并优先（多轮往返定稿）**

- 预付款独立还是付款吸并：先提"参数集同构检验"，被用户反问"粗类吸并细类、槽开够细不就行了"后修正——用户方向正确，定为**吸并优先**
- 最终规则：细类差异能全部装进"同一条边上的参数"就吸并；踩了三条硬线才独立：①**换了当事人**（预付款保函是银行↔买方的边，塞不进买↔卖付款义务的参数——槽描述一条边，挂不上第二个当事人）②**换了模态**（质保金扣留权是权力不是义务参数，模态是关系行字段，槽碰不到）③**条件适用槽成堆**（"仅阶段=预付时可填"的校验规则攒多=用 if-else 重造类型系统，不如让类型系统干）
- 应用：进度款/到货款吸并（阶段槽取值）；保函独立单元（预付款/履约/质保保函是类型取值——单元不管当事人，当事人写在实例上，担保家族由此收拢）；质保金扣留权独立边；预付款先吸并（阶段=预付+条件槽），条件槽攒够再裂变
- 上位关系（is-a）基本不建：聚合查询用槽取值走通；真发生裂变时补"原属"迁徙记录

**单元增加的谨慎原则**

- 槽是耗材，单元是观点：单元清单=词表作者对"商业世界由哪些基本安排构成"的理论主张。单元错的代价是系统性的（记录打着行为类标签、撤单元要迁存量、碎片化拆散查询、两作者两套单元图就分裂）；槽错是局部的
- 出生门槛不对称：槽案内认定可生；**单元出生走全局评审且必须带证据包**（跨种类出现证据+踩了哪条硬线+名下槽清单），无证据包退回
- 裂变是单元增长主通道：新单元最好从粗类里养出来（条件槽成堆=裂变时机），自带迁徙记录；凭空发明是例外
- 质量标准：**单元表必须一屏可览、一名律师可持**——装不进脑子的世界观是目录不是世界观；多到要翻页记说明吸并没做狠，打回重聚（具体数量先不估算）

**v0 生成工序定稿：两遍两闸**

- 用户定调：agent 先过一遍**宽容生成**、多提候选等人删（选择题比回忆题可靠——短清单缺了什么人看不见；生成要广撒网、准入要紧把关，"吸并优先"等谨慎规矩全部移到人这边执行）；人删并出定稿单元表（闸一，世界观决策）；拿定稿单元再跑第二遍逐单元收割槽（闸二）
- 第一遍读手输出五样：主题（自己的话，什么粒度顺口叫什么）/可约定点/原文措辞摘句/当事方/模态词（须/有权/不得）——后两样是中心跑硬线的原料；读手仍不懂词表概念
- 第一遍产出候选单元清单：每条附证据（哪些种类哪些条款）+预判（独立/吸并进X/存疑）+"谁对谁"检验结果；预判只辅助排序不作决定，人可翻案
- 闸一（人）深审单元：对着证据审，硬线当删并判据，存疑的人拍板
- 第二遍逐单元收割：可约定点（带值形态）+真实措辞例句（顺手长成识别特征）+条件适用标记（裂变候选）；每单元一子任务，有界、可并行、可单独重跑
- 闸二（人）快审槽；条件槽标记照单全收留档（=词表的生长路线图）
- 发现哪都挂不上的条款进残留清单，不许悄悄塞进相近单元；残留=漏掉的单元候选，攒 v2
- 收尾：三份规则文件考卷+法律文本查漏→v0 合入；产出三件套（草稿 yaml+证据包+判定表）

**验收机制（多轮往返定稿）**

- 用户原始提案：若干真实合同跑完转化流程后做双向检测——合同的信息是否均进入 .db；从 .db 能否读出全部合同信息
- 我方第一轮提了五处缺陷（语义完备不可判定、存原文后"读出全部"循环通过、漏了无添加方向、需 held-out 防泄题、未定运行模式与通过线），并给出重方案（六道机械账+人审抽样+考卷）
- 用户两轮反驳，多数被推翻：①双向设计本就覆盖漏项（我方把方案误读成只从库出发，收回）；②纯机器验证不需要人；③关键一条——**核对员是 LLM**：LLM 读合同逐条去库里找体现、逐条读库回合同对，不需要事先准备"信息清单"
- 我方认账两条：LLM 当核对员则"语义清单造不出来"不成立；"验理解和做理解是同一难题"也错——核对比提取容易（比对时两边答案都在眼前）
- 定稿机制：**LLM 双向逐条核对 + 机械底座 + 种错测核对员**
  - 机械账（字符覆盖/锚验证/值枚举 diff/值级往返）保留但降级为免费可证的底座，做在案件 CLI 的对账命令里；机械 diff 清单直接喂给 LLM 逐条追因
  - 双向核对：合同→库，逐条款问"在库里如何体现"（漏项候选）；库→合同，逐记录问"依据何在"（错项候选）
  - 同源盲区对策：核对与提取换模型，或把问法倒置
  - 核对员自己也错报漏报：种错模式测检出率——在一次性 db 副本（非真案件，绕开写路径纪律）埋已知错误（金额改位、主体对调、删记录、模态标错），跑核对数抓出几条；抓不住的错型=已知盲区写进报告
  - 方差：跑两遍取稳定项，波动项标注
  - 发现清单只报案不办案：进池走认定，与既有纪律不冲突
- 两种用法：验收模式（held-out 语料、机器独跑、出基线指标，词表改进后复跑对比）与日常模式（每案提取后跑，清单进池供认定参考）

**测试方法（定稿）**

1. 用户提供多份真实合同（未参与词表归纳的）

**范本当初次提取语料（用户提出，我方两处异议被纠正）**

- 用户问：初次提取直接选一系列标准合同范本来跑，是否合理。我方第一轮仅许其当冒烟测试，提三条异议（范本值是空的致值级提取没测到；范本没有真实合同的脏乱；措辞统一致过拟合），并排三步顺序（范本冒烟→少量真实合同→held-out 验收）
- 用户两点反驳：①说的不是一两个范本，是**来自不同机构的各种范本**；②值当然是空的——要求反思该异议从何而来
- 我方修正一（空值异议作废）：该异议来自未检查的预设"提取的产品是填好的值"（数据抽取思维）。按本系统自己的本体，槽空着是合法状态、词表管槽账本管值——范本下划线的正确提取结果就是"槽在、值空"，这是槽识别的正确答案而非缺陷。且空白白送忠实性测试：爱编值的提取器在范本上当场露馅（无添加免费受检，范本里幻觉出来的值一眼假）
- 我方修正二（过拟合异议基本消解）：多机构范本（政府示范文本/行业协会/企业自有模板/律所模板/FIDIC 类国际范本）结构各异、条款组合不同、措辞分派——是多家专业机构世界观的显式陈列，不是低多样性语料
- 更深一层：范本是起草机构做好的"单元-槽清单"——下划线=槽声明，但书与标准条款=槽的默认取值，条款结构=单元清单；对两遍两闸的词表归纳是上等原料
- 修正早前决定："归纳语料不要范本"改为**混编**：多机构范本给结构覆盖（单元候选+槽清单+默认值），真实合同给真实脏乱、谈判改写、非标组合
- 真实合同不可替代处收窄为三条：脏乱输入鲁棒性（扫描/表格/涂改）、谈判后非标条款组合、值级行为——管道跑顺后用少量真实合同补；验收仍用真实合同（不变）；三步顺序保留，但第一步的定位从"降级的便宜替代"升为"正当原料"

- 起因：用户质问池/认定与项目目的的关系，判定为失败设计——考古确认两者均为未经本项目目的检验的外来概念，焊进了不变量却无正当理由
- 裁决一（废池）：所有信息点必须自动归类，不存在待归类容器——"这段无规定内容"本身也是一条机器归类；无漏项由归类全覆盖直接满足
- 裁决二（废认定）：认定步骤与关系表"状态（提议/已认定）"字段删除，运行流程七步变六步——职责已被接管：值的可信度由来源级+对账管，归类的正确性由 LLM 核对员管，③级推断写入时自带前提与责任人
- 随废：无未处置三态、"唯一通道=池→认定→晋升"、晋升术语、"单元出生带证据包走全局评审"

- 节点同一性（外部评审意见采纳）：同一性案内即需而非合同群专属；主体靠规范形机械匹配，事件与定义值靠出生锚；合并用重定向零改写

- A1 由用户方案解决（比评审建议的"规定类型学"改动更小）：合同成为第五类节点；元规定=以合同节点为主语、带锚的记录（生效条件、文件构成、文本型定义、可分割性、解释规则）；单元判据推广——主语可为主体对或合同，"合同机制类"单元由此成立，解开"合同文件构成过不了自身判据"的矛盾；但书从值形态移出（值形态剩四种），成为以合同/条款为主语的除外记录（双指针"算作→A、不算作→B"走引用表）；当事人与角色绑定为合同节点属性（锚指首部/签署栏，签署栏移出"无规定内容"）；合同节点与素材分清（一个合同跨多份素材，文件构成列清单）；"规定间唯一动词"改为"取代是唯一时间性动词，除外/优先/定义引用是解释性指向走引用表"

- 缺口表裁决（账入库，2026-09-11 续）：缺口不能只活在报告里——库内需要可快读的存放处。案件库新增**缺口表**（条款id/类型：未归类·疑似缺槽·疑似缺单元·核对漏项/描述/锚/提出者/时间），两个写入口（提取时疑似缺口、对账时核对漏项），写入即定、只读、无状态流转。与已废池的判据：池是流程容器（内容搬入等认定、有状态流转、参与生效），缺口表是存储账（只记"哪条缺什么格子"，内容本体在条款表，不参与任何流程）。第五查正向随之升级——每条款至少一条记录、"无规定内容"记录或缺口记录，缺口从对账算出变为提取时显式入库；聚合改为扫各案缺口表；查询面加缺口清单

- 主体识别机制重设计（2026-09-11 续，sub-agent 重推+用户裁决）：用户否决旧两机制——**机械匹配不可实现**（正文称谓大多未经声明绑定，"业主=买方"的等同只存在于读者理解中，无文本可查；降为预检）、**"提议待消费方折叠"违反目的**（复活已废的悬挂态；归类单元、标模态、认金额都是提取器理解判断直接写入，身份无特权；身份判定是建模问题，推给外面等于没建模完）。新设计：**识别内嵌于提取**——填负担方/受益方即完成指称判定；主体=有独立 id 的法律主体节点（规范形+别名集，每别名带绑定锚与来源级：合同声明的①级、未声明共指的③级指称绑定——前提+提取器署名，默认参与查询折叠）；事件加**参与者引用**（事件实例身份=事件名+参与者结构，呼应"当事人写在实例上"）；对账加第六查**称谓闭合**（每个出现的称谓必有别名声明或③级绑定行，③级前提锚可解析）；种错加三错型（错并、漏并、角色错绑）；矛盾绑定并存为冲突、修正走重定向命令；"宁可分裂不可错并""判不同留痕"保留为提取纪律

**入库 skill 工作流设计与重组框架重立（2026-09-18，用户裁决）**：

- 首提方案被否：以主合同为底本、补充协议按序应用修改、处置表记账、机械拼装的"重述本"方案——判"乱七八糟"，完全不用考虑是否为补充协议/修改
- 用户框架：模型阅读每一个条款→打标签→按标签重组成多个文件。旧方案的全部复杂度来源（定序、指令消费、重述本、文件角色判断）连根拆除
- 裁决一（多标签＋标签就是 unit）：必须多标签，标签就是交易单元——零新词表，标签封闭性=快照封闭性；多标签条款出现在每个所属组文件是设计行为
- 裁决二（脚本优先）：应该使用脚本的环节必须使用脚本——模型全程只产标签、文本一个字不经模型的手；封闭校验、覆盖闭合、分组导出、缺口路由全是脚本

- 裁决四（打标并行）：条款打标相对独立→多读手并行；批次按条款切、互不相交、无共享写冲突；逐批写入、失败只重跑本批（按条款地址幂等）；读手可用全文做上下文但只对本批产输出
- 裁决五（商业模式总结前置）：context engineering 补丁——并行读手无共享状态、批次是切片缺背景，一致性方差没人管；串行读手通读全部素材出一页总结（交易性质/当事人角色链/主干流程/资金担保结构/特殊机制/素材地图）注入每个打标读手上下文。纪律：只描写交易、不描写标签体系（可复用、不与打标循环依赖）。归宿：入库为案件概要——读手上下文的库存份而非库的主张（不进关系图、不带锚、不设来源级），随重组批次重新生成；提取环节直接复用

**多方安排拆解为二元关系（2026-09-24，用户裁决）**

- 词表纪律：不能改只能增删；条目不可变；改=增+删（可带"取代了谁"）；**槽与单元的出生只有一个通道——全局、律师、经词表工具，案内不造**；案内缺口写入**缺口表**（写入即定、只读、不参与任何流程——非池的复活），聚合扫各案缺口表汇成词表缺口报告回流（单元深审、槽快审），旧案不回填、缺口多则重开新案
- 词表治理流程已收口：低频、按需，结合案件缺口汇总与律师主动提案；agent 整理建议文件，人工直接写意见，agent 按意见整理变更、主会话调用词表工具执行并输出摘要，无需精密流程
- unit/slot 判据："谁对谁有一个X"问得出口是单元；条款标题≠单元；吸并优先，不凭可选模态字段的变化机械决定拆分，依据原文是否规定独立关系并由律师审定具体词表；裂变补"原属"谱系字段；上位关系不建
- 主体识别：主体=独立 id 节点（规范形+别名集，别名带绑定锚与来源级：声明①级、未声明共指③级指称绑定——提取判定的依据与审计痕迹，非运行时解析层）；事件所需主体在前置识别时先确定或同批建立，其余称谓在后续提取时判定；**同一性核查=比 id 相等**，机械匹配降为预检。当事人之间的每条关系记两个主体及各自性质，双务拆两条，多方安排按实际关系拆分；宁可分裂不可错并、判不同留痕为提取纪律；矛盾绑定并存为冲突、修正走重定向（重定向参与查询折叠）
- 事件：以合同实际用作条件或时间基准的一项发生事项为粒度，内部步骤按独立引用需要拆分；节点具案内唯一 ID、出处及必要参与者信息，同一事项复用节点，不同事项区分。原文参与者、对象、批次或阶段等用于理解同一性，名称或参与者相同本身不是自动合并判据。认定职责统一由事件提取 sub-agent 承担，在打标分组前通读识别并经 CLI 入库，向各提取 agent 提供可引用记录；组合与时间偏移留在条件或时间表达中。漏提归入一般提取质量风险，不增加专门检查或补提流程，不再作为独立待决问题
- 二元关系：无论参与方多少，当事人之间的关系统一拆成两两关系；不按人数生成记录，不枚举全部主体组合。多条记录共同表达一项安排时，须保留共同金额、条件和相互影响，通过细节、条件、事件和引用表达；不得变成相互独立且改变原意的义务。合同级元规定、定义事实等按已有记录形态表达
- 当事人性质与模态：当事人性质独立填写，沿用八种核心值及原文功能标签，不按语法主语确定端点。模态可选；肯定/否定通过现有槽和值表达，局部例外与共同约束通过细节和引用表达，不依赖模态替代完整含义
- 外部基准（LPR/汇率/指导价）：第四类节点，只记被引用、永不记数值
- v0 工序：两遍两闸；人工交接已收口——提取结果写入文件，人工直接在文件中写意见，agent 读取并按意见整理后继续原有步骤，无需专门意见格式或审批机制。规则文件=考卷、法律文本=查漏清单、跨种类语料（多机构范本+真实合同混编）=唯一原料
- 运行流程七步（入库 skill 总体流程已收口，末步由词表治理承接）：开工→登记（先经预处理 CLI）→切条款（每份素材、零解释、标签字段空、异常入缺口表）→**通读准备与重组**（通读生成案件概要并识别事件及其所需主体→经 CLI 写入事件记录→并行打标〔多标签=unit、无匹配入缺口表〕→分组导出〔脚本逐字生成组文件，不产文本版本〕）→提取（各读手取得案件概要及共用事件记录，按组读窗、每条款完整提取一次、复用已建事件、提全不受组标签限制、修改关系记指向、其余称谓归主体当场完成、缺口当场入缺口表；前置事件识别不把整条款标为完成；完整 JSON 由主会话逐文件调用 CLI 写入）→对账（机械六查，报告指向记录、修正走命令）→聚合（低频、按需扫缺口表回流，非每份合同入库必须等待的步骤；律师主动提案也可进入治理流程）。新补充协议到达后经预处理登记与切条款，再通读、识别事件、打标分组及提取，仍按入库步骤提交与对账。检索式查询贯穿，缺口清单一条查询即得
- 编排纪律：读手原则——凡大量阅读合同条款的环节一律 sub-agent 读手、主会话不读全文（全部 skill 共用）；通读准备产出概要与事件记录，打标模型只产标签，分组文本由脚本逐字导出；能用脚本的环节必须脚本化
- 提取提交分工：各 unit 并行，agent 生成完整 JSON 并返回路径、条款清单及摘要；主会话每文件一次 CLI。整份成功或整份不写入，失败交回原 agent 修正；同一成功内容重提返回原回执，共享上下文由显式输入提供
- 版本与对账：稳定对象 ID、追加完整记录版本，撤销同样留历史；原件与全文入 SQLite。称谓检查限已识别对象，数值差异仅提示；对账有错误允许继续操作，但不能报告本轮完成
- 交付物七件（三个 CLI：预处理/案件/词表 + 四个 skill：预处理薄壳/案件/词表/初始化）；开发顺序：design.md → yaml 格式与校验 → 初始化 skill → v0 词表 → 案件工具完整可用
- 原则：词表内容（槽与单元）全部归律师治理，出生只走全局通道，机器只报缺口不著作词表；需求驱动 schema 已否定；第零条判定法（消费者问题不是建模问题）
