## 1. 范围与设计依据

### 1.1 目标

将一份合同及其组成素材转成一个 SQLite 案件库。库内同时保存已登记的完整文本、结构化规定和原文出处。消费方可读取合同规定，并从每条规定回到相应条款。

合同文本规定的金额、期限、条件、例外、权利义务属于建模内容；现实中是否付款、某事件何时发生、某条规定是否合法有效，以及多个独立合同的组合分析，由消费方处理。

### 1.5 安装、专用环境与 skill 调用

每份完整安装在安装根下创建一个专用 Python 虚拟环境 `.venv`。三个 CLI 安装在该环境中，四个 skill 共用；环境在安装时创建一次，后续会话、不同合同和不同 skill 均复用。安装过程负责选择和检查 Python、SQLite、程序资源和实际命令路径。全局正式词表、合同工作目录及其数据独立保存。

skill 是由宿主读取的工作流说明。模型会话继续在宿主中运行；环境绑定发生在它启动本项目 CLI 的那一步。安装过程把三个程序的绝对路径写入安装根的 `runtime.json`，skill 从自身真实目录向上两级找到该文件，并使用其中的命令路径。这样无需在每次调用时选择 Python、设置 PYTHONPATH、激活环境或切到源码目录。

| 安装后命令 | Python 入口 | 使用方 |
|---|---|---|
| `legal-case` | `legal.case_cli:main` | 案件 skill；初始化中的案件建模交接仍由案件 skill 承担 |
| `legal-vocab` | `legal.vocab_cli:main` | 初始化与词表治理 skill |
| `legal-preprocess` | `legal.preprocess_cli:main` | 预处理 skill |

在 `legal/src/pyproject.toml` 声明安装包和三个命令入口，运行时仍只依赖标准库；SQL 与单位配置随包安装。完整交付包含同一版本的安装包、四个 skill、共享资料及使用说明。安装辅助实现和测试也放在 `legal/src`。标准 Python 构建与安装工具属于交付工具链，零第三方运行依赖继续适用。

安装顺序为：确定完整交付目录和安装位置 → 检查解释器及 SQLite → 创建专用环境并安装包 → 核对资源与三个命令 → 生成安装信息并注册四个 skill → 完成安装验收。宿主注册使用宿主已有机制，首版仍不指定某个宿主的插件格式或技能目录。注册须能保留 skill 的真实目录及共用引用关系。

调用时，主会话先按用户提供路径的原始基准解析输入，再以参数数组将绝对路径传入 CLI。案件命令在合同工作目录运行，初始化和词表治理在各自工作目录运行；工作目录中的相对文件不会因寻找程序而改指源码目录。安装信息失效或程序缺失时明确报告安装问题，由显式安装操作恢复；skill 不在业务执行途中重建环境或自动换用另一套程序。

预处理 CLI 使用这个共用环境；它启动的外部转换程序仍由显式配置给出，其自身运行依赖单独安装和验证。安装验收包括源码目录之外执行三个入口、实际初始化/查询、中文及空格路径、四个 skill 的引用、同一环境复用和新会话调用；字段、步骤及断言见 spec §1.5、§14.5。

## 2. 数据表示的共同约定

### 2.1 文件、编码与数值

- 文本与交换文件使用 UTF-8。已登记的文本内容保留原样，锚验证时不隐式去空格、改标点或做字符归一化。
- JSON 对象禁止重复键，拒绝 `NaN`、`Infinity` 等非标准数值。
- 合同中的十进制金额、比例等采用十进制字符串保存，例如 `"1234.50"`；运算与校验采用十进制计算，避免二进制浮点误差。
- 原文数字写法与归一化数值分开保存；字符格式不等于合同含义。
- 案卷管理时间使用带时区的时间字符串；合同约定的日期、期限属于槽值，使用第 6 章的时间表示。

Python 标准库 `json` 默认接受部分非标准输入，读取时需显式检查重复键和非有限数值。见 [Python JSON 文档](https://docs.python.org/3/library/json.html#standard-compliance-and-interoperability)。

### 2.2 标识与引用

按 decisions §1.16 区分三个标识：

| 字段 | 含义 | 寿命 |
|---|---|---|
| `object_id` | 一个案内对象的稳定 ID | 修正时不变 |
| `record_id` | 该对象的一份完整记录版本 | 每次追加生成新 ID，内容不可变 |
| `local_id` | 提交文件内某一待写记录的临时编号，包括新对象或现有对象的新版本 | 仅本文件内有效，回执给出对象和版本 ID |

正式 ID 采用 UUID，不编码主体名称、条款含义或事件名称。事件同一性由负责事件提取的 agent 判断，不能通过名称哈希替代判断。后文的 `node_id`、`clause_id` 等是相应类别的对象 ID；需要锁定历史内容时另外给出 `record_id`。

同一提交文件内的待写记录用文件内编号互相引用，写入工具返回对应表；新对象分配对象 ID 与版本 ID，修正已有对象只分配新版本 ID。文件之外已经存在的对象直接使用案内 ID。两类引用使用不同字段：

```json
{"local_id": "receipt-of-prepayment"}
```

```json
{"object_id": "已存在的案内对象 ID"}
```

业务引用二选一使用以上形式，默认解析到对象的最新记录。出处、推断前提或复合值内部路径需要固定历史内容时，使用 `{"record_id":"具体记录版本 ID"}`；本批新记录可以先用 `local_id`，入库时按字段规则固定到本次产生的记录版本。工具不把固定版本的引用改写为最新版本。

修正记录也有 `local_id`，使同批其他记录能固定引用该次新版本，例如条款修正与新锚一起提交。单独用 `local_id` 声明对象是新建；同时提供 `object_id/previous_record_id` 则修正既有对象，并不产生第二个对象。

关系、细节、节点、引用与锚可在同一文件内交叉引用，工具先建立编号表，再校验引用及类型，不要求 agent 按 SQL 插入顺序排列记录。业务字段如允许固定版本引用，必须在字段契约中明示；不能任意混用。

所有引用必须能在本次提交与目标案件库中解析。对象名称不是写入时自动创建或合并对象的指令。

复合值内部引用的可选 `value_path` 只与固定 `record_id` 一起使用，形式及限制见 §12.2。各记录字段明确选择业务引用或固定版本引用；完整来源前提始终固定到记录版本。

### 2.3 来源级

| 来源级 | 输入必需内容 | 机械可验证的范围 |
|---|---|---|
| 原文引述 | 至少一个出处锚 | 引文在指定条款中存在 |
| 机械变换 | 出处锚、表层值、归一化结果、格式契约 | 变换和还原与声明的格式一致 |
| 显式推断 | 推断说明、前提记录、责任人或 agent 署名 | 前提可解析并可追溯到原文，署名非空 |

来源级用于说明表达所依赖的依据。它不把交易单元归类、模态或事件同一性的理解判断变成可机械证明的事实。

每个主体引用及其性质、关系的交易单元、已填写的模态、每个槽值都要有出处。不同字段的依据不同时分别记录，不能用关系整体的一处引文掩盖某个字段没有依据。

前提引用可以指向本次提交的新记录。前提链必须最终可达出处锚；不接受只有互相引用、没有文本依据的闭环。

来源的交换结构如下；`anchors` 和 `premises` 使用第 2.2 节的引用格式：

```json
{
  "level": 1,
  "anchors": [{"local_id": "anchor-payment"}]
}
```

```json
{
  "level": 3,
  "premises": [{"record_id": "作为前提的已有记录 ID"}],
  "explanation": "结合两处明确称谓判断其指向同一主体",
  "asserted_by": "负责判断的 agent 或人员"
}
```

第二级来源在第一级结构上增加 `surface`、`format_contract` 和格式参数；格式契约必须是工具支持的确定性变换，拒绝未知或无法往返的声明。第三级的 `explanation` 与 `asserted_by` 不得为空。来源格式无法机械判定原文是否足以支持结论，报告应保留这一边界。

## 3. 素材、文本版本、条款与锚

以下表格给出逻辑字段及约束，SQL 类型使用 `TEXT`、`INTEGER`、`BLOB`；对象及列表用受校验的 JSON 文本保存。通用版本列及物理索引见第 12 章。

### 3.1 素材

| 字段 | 含义与约束 |
|---|---|
| `material_id` | 素材记录 ID |
| `name` | 文件名或人工提供的材料名称 |
| `media_type` | 文件类型，用于选择预处理方式，不推断合同效力 |
| `content_hash` | 原始文件字节的 SHA-256 |
| `original_bytes` | 原始文件字节，使用 SQLite BLOB 保存 |
| `original_path` | 登记时的路径，仅作来源提示，不作为移交后读取原件的唯一依据 |
| `registered_order` | 案卷登记顺序；不表示合同法律上的优先顺序 |

同一合同可以登记正文、补充协议、附件和从属文书。材料名称或登记先后不自动决定其修改关系。

按用户确认，原始文件与转换全文一并保存在 SQLite 中。写入时按原始字节计算并核对哈希；导出原件时保持字节完全一致。移交一个完整案件库即可携带原始材料，原路径失效不影响取回原件。

### 3.2 文本版本

| 字段 | 含义与约束 |
|---|---|
| `text_version_id` | 文本版本 ID |
| `material_id` | 所属素材 |
| `version_number` | 同一素材的转换版本序号 |
| `conversion_method` | 格式转换或 OCR，按实际记录 |
| `converter_version` | 转换工具与版本 |
| `text` | 转换后的全文原样保存 |
| `text_hash` | UTF-8 编码全文的 SHA-256 |
| `anomalies` | 预处理报告的异常及位置 |

重转换产生新版本，原有文本与锚不移动。分组导出不产生文本版本。全文字节哈希与原始文件哈希分别记录，两者不能互相替代。

条款列表、分组和进度默认按每份素材最新登记的文本版本取范围；可显式指定旧版本。重转换不会自动使旧业务记录消失：重新提取时读取已有建模对象并按 §8 修正或撤销，旧锚继续固定到旧文本。字符覆盖默认逐素材检查本轮所用版本，历史原文可单独检查。

### 3.3 条款

| 字段 | 含义与约束 |
|---|---|
| `clause_id` | 条款记录 ID |
| `text_version_id` | 所属已登记文本版本 |
| `sequence` | 在该文本版本内的顺序地址，从 1 开始；不依赖原文编号唯一 |
| `original_number` | 原文编号，可空、可重复 |
| `text` | 属于该条款的原文片段 |
| `start_offset`、`end_offset` | 全文中的字符位置缓存，区间含起点不含终点 |
| `tags` | 该条款的 unit ID 列表，初次切分时为空 |
| `classification` | 普通条款、无规定内容、无匹配；打标后填写 |

条款地址由素材、文本版本及 `sequence` 确定。编号重复时仍能分别寻址，原文编号保留用于展示。

切分按全文连续区间组织，条款片段拼接必须逐字符等于登记全文。常规独立打标单位是合同的 article：有章时一般为章下第二层合同标题，无章时一般为第一层合同标题；这里的层级不是固定的 Markdown `#` 个数。article 包含自己的标题、子标题、段落、列项、条件、例外、表格及表后规定，直到下一个同层 article 或上级章节。空行和表格边界不产生新的完整提取责任。章标题、目录、前言、签署页等仍有不重叠地址；其中若含独立规定，可例外打标和提取，纯目录或标题记无独立内容。章标题可作为阅读上下文重复提供，但基础字符覆盖只计一次。无编号本身不构成异常；无法确定结构归属时才记结构异常。原件自动编号由新的显式转换结果写入 text.txt，不添加结构映射元数据，也不改写已登记文本。

`tags` 是条款表字段，不增加标签表。多标签表示多个分组都能读取该条款，不表示要重复提取同一条款。

切分创建条款对象及第一份记录，打标追加该对象的完整记录版本；文本、地址与原文编号原样带入，补入标签及归类。旧记录不修改，也不为标签另设业务表。锚固定到其建立时的条款记录版本，因此后来的标签修正不改变锚所指原文。

### 3.4 出处锚

| 字段 | 含义与约束 |
|---|---|
| `anchor_id` | 锚 ID |
| `clause` | 指向具体条款记录版本的引用，包含其稳定条款 ID 的查询结果可供展示 |
| `quote` | 连续的原文引文，不得为空 |
| `occurrence` | 相同引文在该条款内的第几次出现，从 1 开始；唯一出现时可省略 |

锚的解析算法：

1. 读取锚指定的原始条款文本。
2. 逐字符搜索 `quote`，包括可能重叠的匹配。
3. 没有匹配即报错；只有一次匹配时定位到该次。
4. 存在多次匹配时要求提供有效的 `occurrence`，或由产出方加长引文后重提。
5. 缓存匹配位置以便展示；验证依据始终是条款地址、引文和出现序号。

引用多个不连续文句时使用多个锚，不把省略号拼成原文中不存在的连续引文。记录可共用锚，锚本身不能证明业务解释正确。

## 4. 词表快照与案件出身

### 4.1 全局词表的逻辑结构

| 对象 | 字段 |
|---|---|
| 交易单元 | ID、名称、别名、识别说明、必要的原属或取代说明 |
| 规定槽 | ID、名称、值结构声明、解释与例句、必要的取代说明 |
| 归属 | 单元 ID、槽 ID；允许一个槽关联多个单元 |

不挂任何单元归属的槽属于通用槽。按 decisions §1.22，删除最后一个归属时，同份变更须明确删除该槽、改挂其他单元或将其设为通用槽；缺少明确处置即整份变更失败。比较变更前后归属即可识别这种情况，不在案例入库时推测治理意图。

领域中的具体单元与槽由初始化、治理流程经律师决定；本文的示例名称只用于说明结构，不作为内置词表发布。

### 4.2 开工快照

开工读取完整词表，检查单元、槽及归属引用后，将三类条目完整复制入案件库。冻结后的案件词表仅用于读取和校验，不能在案件中增删。

案件出身保存：

- 案件 ID、创建时间；
- 源词表文件清单与内容哈希；
- 词表结构格式版本；
- 值结构格式版本；
- 当事人性质与模态代码版本；
- 单位配置版本、内容哈希及对应配置内容；
- 案件文件格式版本与创建工具版本。

单位配置随工具提供，不由案件 agent 生成。保留本案使用的配置内容，使案件的旧单位代码仍能被解释；这不引入实时汇率或外部基准数值。

### 4.3 词表文件语法与加载

按 decisions §1.13，词表仍可使用 `.yaml` 文件名，内容采用标准 JSON 写法。初始化与治理工具统一输出缩进为两空格、保留中文字符的文件。人工意见放在对应审阅文件中，不插入正式词表的 JSON 内容。

JSON 是 YAML 1.2 的子集，标准库可以完成本项目已限定语法的读写；普通 YAML 的注释、缩进映射、别名等不在输入范围。见 [Python JSON 文档](https://docs.python.org/3/library/json.html)。

一次词表加载得到以下完整逻辑对象：

```json
{
  "format_version": 1,
  "units": [],
  "slots": [],
  "assignments": []
}
```

| 类别 | 必填 | 可选 |
|---|---|---|
| unit | `id`、`name`、`description` | `aliases`、`examples`、`origin_unit_id`、`replaces` |
| slot | `id`、`name`、`description`、`value_schema` | `examples`、`replaces` |
| assignment | `unit_id`、`slot_id` | 无 |

`aliases/examples/replaces` 为字符串列表，默认空；`origin_unit_id` 为可选历史单元 ID。`replaces/origin_unit_id` 表达谱系，可指向已从当前词表删除的历史条目，不按当前归属外键处理；使用方不得仅凭谱系自动替换案件中的旧 ID。新增条目由工具分配新 UUID，修改内容须新建，写接口不复用已删 ID；加载本身不能凭一个孤立文件证明其从未被手工改过，差异审阅与版本历史承担这部分追溯。

目录布局可按单元分文件；加载器合并后按完整逻辑对象校验。所有 ID 在相应类别内唯一，同一 ID 不能由两个文件提供不同内容；归属中的 ID 必须存在；相同归属不能重复。

词表哈希以校验后的逻辑对象为输入：对象键排序、无多余空白、UTF-8。条目列表按 ID 排序，归属按单元 ID 与槽 ID 排序；具有语义顺序的值列表不重排。因此文件分拆和缩进变化不改变词表快照的逻辑哈希，实际条目变化会改变哈希。

## 5. 建模记录

### 5.1 主体节点

主体节点字段为 `node_id`、`node_kind`、`canonical_name`、`identifiers` 及各字段出处。

`node_kind` 为主体类型时，`canonical_name` 取合同中有依据的规范称谓。证件号、注册号等仅在素材明确提供时记入 `identifiers`，每项都带出处；不以缺少统一社会信用代码拒绝自然人或其他主体。

主体名称或标识相同只提供识别依据，程序不按字符串相同自动合并。主体同一性的判定及未声明共指遵循既有提取与显式推断规则。

别名声明存入引用记录：原文声明的别名使用原文来源；未声明的共指保存前提与 agent 署名。别名应保留所适用的合同或材料范围，避免把不同材料中的同名角色直接混为一个主体。

### 5.2 事件节点

事件的逻辑字段：

| 字段 | 含义 |
|---|---|
| `node_id` | 独立案内 ID |
| `name` | 用于阅读的事项名称，不作为自动合并键 |
| `description` | 原文所指事项的具体描述 |
| `participants` | 主体 ID 及其在事件中的原文角色 |
| `object` | 原文明确区分的对象，可用文本或引用表达 |
| `batch_or_stage` | 原文明确区分的批次或阶段，可空 |
| `sources` | 该事项的出处及同一性判断所需依据 |

这些字段只补充原文提供的信息，不为未来发生的每次行为生成实际发生记录。参与主体先确定或同批建立。

“交付后十日付款”使用交付事件及十日的时间表达；“验收合格且收到发票”使用两个事件和“且”表达。后续关系提取 agent 使用已有事件及 ID。

### 5.3 其他节点

- **定义值**：名称、六种值形态之一的值、适用范围、来源。被多个关系共用的同一金额只定义一次，关系通过引用共享。
- **外部基准**：名称、合同约定的基准描述及出处。只记录引用，不抓取或保存现实数值。
- **合同**：本案合同的容器；开工分配唯一容器节点 ID，初始只有管理标识，不填写无依据的法律名称。名称、当事人与交易角色绑定、材料构成随后通过带出处的记录表达。各读手取得同一容器 ID，交易角色与某条关系的当事人性质分别保存。

### 5.4 二元关系与当事人性质

每条当事人关系包含交易单元、两个主体引用及各自性质、可选模态，以及附属细节。两个端点的位置只便于存储，不能代替当事人性质，也不按语法主语强制确定。

核心性质代码与含义：

| 代码 | 中文含义 |
|---|---|
| `obligor` | 义务人 |
| `recipient` | 受领人 |
| `power_holder` | 行使方 |
| `power_subject` | 承受方 |
| `permission_holder` | 享有方 |
| `permission_counterparty` | 相对方 |
| `protected_party` | 受保护方 |
| `restricted_party` | 受限方 |

另有 `functional_labels` 保存按原文填写的功能标签，附原文依据；功能标签不增加第三个关系端点。

模态使用可空字段 `modality`，非空值为 `obligation`、`power`、`permission`、`immunity`。空值表示未分类；工具不从当事人性质补填模态，不按情态词推导或拒绝模态。

按 decisions §1.15，肯定与否定通过既有槽和值结构表达，不增加统一字段。例如“应当转让”与“不得转让”的行为内容必须分别保留积极行为和禁止行为的含义，不能因为主体、核心性质与单元相同就合并。具体槽名及值域由律师治理的词表决定；词表暂时无法表达时记缺口，不由 agent 临时造槽，也不能仅靠省略模态表示禁止。

### 5.5 合同级规定与细节

合同级规定用合同节点作为主语，可包括生效条件、定义、文件构成、优先次序和局部除外。它们与当事人二元关系分开校验，不能虚构第二个主体。

细节记录字段为：记录 ID、所属关系或合同规定、槽 ID、值、值结构、来源。一个槽的值可包含重复组，保留同一阶段中的金额、比例、条件和期限之间的对应关系。

局部除外按既有双指针设计分别记录适用和不适用的目标；目标应能指向某条关系或具体细节，不能把针对某一用途的除外扩大到整个合同。

## 6. 六种值与复合表达

### 6.1 量

```json
{"form": "quantity", "amount": "1234.50", "unit": "USD"}
```

`amount` 是有限十进制字符串，语法为 `-?(0|[1-9][0-9]*)(\.[0-9]+)?`，不使用指数、分组符或非有限数。`unit` 来自本案使用的单位配置。金额、比例、天数均使用明确单位；“万元”与“元”的机械换算要保存原始表层值及格式契约。上限、至少等含义由槽的含义、比较表达或范围结构明确表达。

### 6.2 时

`form` 为 `time`，按 `kind` 区分：

| `kind` | 字段 | 表达内容 |
|---|---|---|
| `date` | `value`、`precision` | 原文提供的日期及年/月/日精度 |
| `relative` | `event`、`offset`、`relation` | 相对事件的前后、以内、届满等约定 |
| `duration` | `length` | 单纯时长 |
| `interval` | `start`、`end`、`boundary_text` | 原文约定的起止及边界说明 |

日期精度由原文决定，不把“2026年9月”自动补成某一日。`offset` 与 `length` 使用量值；“日”“工作日”“自然日”按文本区分，不替合同选择计日规则。

日期 `precision=year/month/day` 分别使用 `YYYY/YYYY-MM/YYYY-MM-DD`，验证该精度内的日历合法性。各时间结构可选 `boundary_text` 保存原文明确的含当日、不含当日等边界；没有原文依据则不补入默认计日规则。

```json
{
  "form": "time",
  "kind": "relative",
  "event": {"local_id": "receipt-of-prepayment"},
  "offset": {"form": "quantity", "amount": "30", "unit": "day"},
  "relation": "within_after"
}
```

时间字段保存合同约定；实际发生日期、工作日历与到期日计算由消费方提供。`interval` 的端点可以是日期、相对时间或事件引用，只有原文规定了起止时才据此填写；无法从原文确定的边界不填写为无限期。

### 6.3 条件

条件采用有类型的表达式：

| `operator` | 字段 | 约束 |
|---|---|---|
| `event` | `event` | 引用一个事件节点 |
| `all`、`any` | `operands` | 非空条件列表，分别表示且、或 |
| `not` | `operand` | 一个条件，表示否定 |
| `compare` | `left`、`comparison`、`right` | 比较量、时间或其引用；比较为等于、不等于、小于、不大于、大于、不小于 |
| `count` | `condition`、`comparison`、`number`、`mode`，可选 `period` | 表达次数及连续/累计要求；次数为非负整数 |

例如“验收合格且收到发票”：

```json
{
  "form": "condition",
  "operator": "all",
  "operands": [
    {"form": "condition", "operator": "event", "event": {"local_id": "acceptance-passed"}},
    {"form": "condition", "operator": "event", "event": {"local_id": "invoice-received"}}
  ]
}
```

次数、时间阈值与逻辑组合均保留在条件中。`comparison` 使用 `eq/ne/lt/le/gt/ge`；`mode` 使用 `continuous/total`。`not` 对条件取反不自动表示主体“没有义务”；行为的规范含义按第 5.4 节表达。

### 6.4 算式

`form` 为 `formula`，字段为 `operator` 与 `operands`。支持加、减、乘、除、最小值、最大值；叶为量或指向定义值、细节值、外部基准的引用。

```json
{
  "form": "formula",
  "operator": "multiply",
  "operands": [
    {"form": "reference", "target": {"local_id": "contract-total"}},
    {"form": "quantity", "amount": "10", "unit": "percent"}
  ]
}
```

条件分支通过具备条件与对应算式的重复组表达。格式校验检查算子、操作数数量与引用类型，不从现实市场取得 LPR、汇率等数值，也不自动生成违约判断。

### 6.5 名/文本

```json
{"form": "text", "surface": "上海港", "normalized": "上海港"}
```

`surface` 保留原文表述；`normalized` 可选。文本槽有枚举约束时，允许值由本案冻结词表声明。语义归一化不能冒充机械变换；不是确定性格式转换的判断按对应来源保存依据。

### 6.6 引用

```json
{"form": "reference", "target": {"local_id": "contract-total"}}
```

`target` 必须指向可解析对象；期望的目标类别由值结构声明决定。事件时间基准只能指向事件，定义值或附件引用按其相应类别处理。

引用表保留解释性关系，如别名、同一性、适用、不适用、优先、术语定义和合同修改。数值表达中的引用与引用表中的目标必须一致；落库时不能留下只靠名称猜测的目标。

针对复合值内部某一部分的引用，需要明确值路径及版本。路径采用标准 JSON Pointer；涉及数组位置随修正变化时，要保留所指版本或改为引用独立定义值，具体与第 8 章的版本方案对齐。见 [RFC 6901](https://www.rfc-editor.org/rfc/rfc6901)。

### 6.7 复合值与词表声明

六种基础形态之外，允许对象和列表作为拼装容器。容器结构由槽的 `value_schema` 声明。

```json
{
  "type": "list",
  "items": {
    "type": "object",
    "fields": {
      "stage": {"form": "text"},
      "percentage": {"form": "quantity", "allowed_units": ["percent"]},
      "condition": {"form": "condition"},
      "deadline": {"form": "time"}
    },
    "required_fields": ["stage"]
  }
}
```

这个示例说明阶段内各项对应关系，具体字段组合由实际词表决定。`required_fields` 只要求已提交的复合值在结构上完整，不表示每份合同必须约定所有槽。

实际值的对象使用 `{"type":"object","fields":{…}}`，列表使用 `{"type":"list","items":[…]}`；基础值带 `form`。工具递归检查声明与值是否一致，拒绝未声明成员、错误类型及缺少的必需成员。未提交的槽保持缺席；不把缺席自动填为 `0`、`false` 或空字符串。

原文明确留空的范本字段可以写一条 `value:null` 的细节，并锚定留空位置及其字段说明。这表示“原文有此字段，值留空”；没有细节记录则表示“本关系未填此槽”，两者分别返回。按 decisions §1.29，同一规则也用于定义值及复合值内部的实际值位置；null 不用于 ID 或算子等结构标识。`null` 不跳过出处校验，不用于代替遗漏、猜测或词表缺口，精确规则见 spec §5.1。

`value_schema` 每层声明基础 `form`、容器 `type` 或 `one_of` 中的一种。`one_of` 是若干已有结构的择一声明，值必须恰好匹配一个分支；例如金额槽可声明允许直接量值或指向定义值的引用。它不增加基础值形态。基础声明可选 `allowed_units`（量）、`enum`（文本）、`target_kinds`（引用）；引用节点类型写为 `node:subject/node:event/node:defined_value/node:external_benchmark/node:contract`，其他类别直接用记录类别。对象声明含 `fields` 和 `required_fields`，列表声明含 `items`；字段名在对象内唯一，required 必须是已声明字段的子集。基础形态由程序按第 6 章固定语法检查，不能用词表新增第七种形态。

共享金额必须有可引用的共同定义，并保留其“共同总额”等约束对哪些关系适用。单纯两次引用同一数字，尚不足以表达共同清偿或合计上限；相应约束及其关系范围须同时记录。

## 7. 提取文件与批量写入

### 7.1 文件结构

每份文件包含格式版本、目标案件 ID、使用的词表快照哈希、提交者、负责条款清单、记录数组及问题摘要。记录数组区分节点、关系、细节、引用、锚、缺口与无规定内容记录。

文件内每条待写记录有唯一 `local_id`，包括修正记录；文件之外的已有对象按第 2.2 节引用。CLI 返回全部本次编号与对象 ID、记录版本 ID 的对应表、各类写入数量和条款清单。

事件前置提交与关系提取提交要能区分，以免主会话因为事件写入成功而把对应条款登记为完整提取完成。

### 7.2 已确定的失败边界

**一个文件对应一个原子提交。** 任一记录有格式、引用、词表、出处或数据库约束错误，整份文件不写入。返回能够定位到文件内记录、字段和具体错误的列表；主会话交回原 agent 修正，再提交整份文件。

写入工具先解析文件及引用，再执行校验；通过后在同一 SQLite 事务中保存本次全部记录与成功结果。事务提交失败也按整份失败处理，不能向主会话返回部分成功。

SQLite 连接显式启用外键约束；事务提交提供同批记录共同成功或共同失败的基础。见 [SQLite 外键说明](https://www.sqlite.org/foreignkeys.html)与[原子提交说明](https://www.sqlite.org/atomiccommit.html)。

### 7.3 重复提交与成功回执

按 decisions §1.12，完全相同的成功内容再次提交返回已有结果。工具对解析、格式校验后的提交内容生成 SHA-256，作为本案内的提交指纹；JSON 对象键与空白归一化，数组顺序保留。

内容指纹包含目标案件、格式版本、词表哈希、提交者、条款清单与全部记录，排除文件的本地路径。因此更换文件名或缩进不会重复新增；内容发生变化视为新提交。

重复检查在 JSON 解析和基本格式检查之后、依赖当前库状态的校验之前完成。已成功的修正文件重提时直接返回原回执，不因其 `previous_record_id` 已非最新而误报冲突。

案件库保存成功回执：提交指纹、首次提交顺序、文件内编号到案内 ID 的映射、各类数量、条款清单和结果摘要。回执与业务记录在同一事务中写入。

- 首次写入成功：返回成功回执。
- 相同内容再提交：返回原回执，注明本次复用了已有结果。
- 首次校验或事务失败：不保存成功回执，整份修正后可重新提交。
- 写入完成但调用方未收到响应：重提相同内容可以取得原结果。

改变内容不是覆盖已写入记录的方式。涉及修正时必须表达已有对象的取代关系；仅更换文件内编号后重提，会形成不同内容，工具不承诺识别语义上相同的两次提取。

## 8. 追加、修正、重定向与查询

本章须区分三件事：

1. 建模记录写错后的取代：按追加式修正规则处理。
2. 同一主体或事件的节点合并：按有依据的重定向处理。
3. 合同文本明示修改另一条规定：保存条款间解释性指向，由消费方判断合同现行规定。

不能因为较晚登记了材料，就自动删除、取代或隐藏旧合同规定。

### 8.1 单对象修正

新对象的 `revision=1`、`previous_record_id=null`。修正提交携带稳定 `object_id`、所依据的最新 `previous_record_id`、完整数据及完整出处；工具生成新的 `record_id` 和递增的 `revision`。禁止半字段补丁、改变对象类别、跨对象取代和从旧版本另开分支。

如果提交所依据版本已不是当前版本，整份失败并返回当前版本 ID，由原 agent 读新记录后修正；工具不静默覆盖。每批对同一对象至多追加一份版本。

细节修正不强制关系换版本，因为细节按稳定关系 ID 归属；关系端点等自身字段变化才追加关系版本。新版本必须重新给出依据，即使仍引用同一原文锚，也要显式带入。

历史查询按 `record_id` 读取原行；当前查询按对象取最大 `revision`。固定版本的出处与前提不随修正漂移。历史查询同时返回稳定对象 ID 和记录版本 ID，不把后来修正的判断装入旧记录。

按 decisions §1.30，历史关系的细节和业务引用按该版本写入的提交序号展开，当时尚未建立的细节不混入；当前查询仍读最新。返回 expansion_sequence 明示关联展开范围；这是模型修订历史，不是合同法律生效时态。精确查询契约见 spec §9.3。

按 decisions §1.20，错误对象追加 `status=withdrawn` 的完整版本，带 `withdrawal_reason`，保留原数据与出处；正常版本为 `status=active`。撤销不是合同义务现实终止，也不是条款效力判断。

拆分时同一文件包含原对象的撤销版本、新对象及全部必要引用修正。校验候选视图中所有现存业务引用，包括细节归属、条件、算式和解释性引用；不得继续指向已撤销对象。同批追加修正或撤销依赖记录，遗漏即整份失败。历史出处与固定版本的推断前提可以继续查到原版本，但查询须显示其所依赖对象已撤销或已修正，不能把旧依据静默替换成新依据。

撤销对象不得再被新增业务引用；历史查询可显式包含它。素材与文本版本是原始证据，不通过建模撤销操作删除原件；缺口表沿用只追加、不做状态流转的既有纪律。机器与人工修正共用同一版本接口。

按 decisions §1.26，误撤销后可用最新撤销版本作为前驱，追加 `active` 完整版本恢复，重新校验全部内容与出处；对象 ID 不变，撤销历史保留。依赖记录不自动恢复，需恢复者同批明确提交。缺口的条款及相关对象引用固定到发现时的记录版本（§1.27），因此不会因其不可修改而阻止对象纠错；查询显示目标后来已修正或撤销。

### 8.2 节点重定向与冲突

主体同一性需要纠正时，追加有出处的重定向引用；原对象和历史版本保留。重定向只用于同类别节点的同一性认定，不用于把合同规定的修改冒充建模纠错。事件同一性仍由事件提取职责承担。

当前查询保留原始引用 ID，同时给出重定向后的目标。定向链必须终止，拒绝环；多条互相矛盾的绑定不能用登记顺序自动裁决，返回候选与冲突。没有冲突的有效重定向参与默认查询折叠，原文事实与推断来源仍分别展示。

### 8.3 查询语义

查询使用本案冻结词表解释字段，返回记录、对应出处与可追溯的原文。根据当事人、单元、槽和来源级组合检索；“没有记录”“已记录缺口”“词表有槽但本关系未填”分别返回，不能把任一情况机械解释为合同没有约定。

## 9. CLI 与四个 skill

### 9.1 已批准的能力范围

案件侧：开工、登记、写记录、查询、对账，以及入库流程已经确定的切条款与分组导出能力。词表侧：初始化、列、查、增、删、差异比较、聚合。具体命令名称、参数和返回结构将在已有能力内展开；涉及增加或改变能力的部分先向用户核实。

### 9.2 入库 skill

开工冻结词表 → 预处理登记 → 切条款 → 准备阅读材料、分段初读、统一归纳概要与主体/事件 → 主会话写入准备结果 → 并行打标、脚本导出分组 → 关系提取 → 主会话逐文件写入 → 对账。初读内部流程见 §16.3 及 [初读设计](initial-reading-design-2026-10-02.md)。

提取输入明确包含本次案件概要、共用事件及出处、负责条款、相关组的原文上下文和冻结词表。每个条款只分配一次完整提取职责；多标签分组中的副本用于阅读上下文。

当事人识别、事件识别或记录理解属于 agent 工作；CLI 执行确定性的格式、引用及出处校验。各完整条款任务按 decisions §1.17 并行提取，主会话逐文件统一写入。任务 unit_id 表示分组上下文，各条关系的 unit_id 按实际规定选择；每个任务明确列出负责条款与仅供上下文阅读的条款，避免把同一分组副本重复入库。本轮小幅优化见 §16.3 及[优化方案](workflow-optimization-2026-10-02.md)。

事件之外的已有主体、定义值等可随查询结果供读手引用；原文上下文不足时，读手按已有查询能力取得有关条款。不存在于库中的必要非事件对象可以与当前结果同批创建。并行任务不互相依赖尚未入库的临时编号，主会话也不通过名称匹配偷偷合并对象。语义上是否为同一对象仍靠有依据的理解判断，必要修正沿用既有重定向和追加路径；不增加全量共用对象预建步骤。

### 9.3 初始化与词表治理

初始化：语料第一遍 → 候选单元文件 → 人工写意见 → agent 整理单元 → 第二遍逐单元提取槽 → 人工在结果文件写意见 → agent 整理词表与证据、判定文件。

词表治理：案件缺口汇总或律师主动要求 → agent 对照当前全局词表写建议文件 → 人工写意见 → agent 整理变更，主会话经工具执行 → 返回摘要。

人工审阅文件使用普通可读文本；正式词表文件使用第 4 章的结构。自然语言意见由 agent 理解，不交给机械解析器判定其法律或业务含义。

## 10. 对账与验收

现有六查逐项落地，保持其证明范围明确：

| 检查 | 口径 | 规格位置或边界 |
|---|---|---|
| 字符覆盖 | 按文本版本检查条款连续区间，拼接等于全文 | §3.2、§13.2；原文版本明确选择 |
| 锚验证 | 地址可解析、引文存在、重复时序号有效 | 无 |
| 值枚举差异 | 可机械识别的数字、日期与提取值作差异提示，不阻断入库 | 具体词法规则见 §13.2 |
| 值往返 | 机械变换必须保留表层值和格式契约 | §13.3；仅验证工具声明支持的变换 |
| 归类覆盖 | 每条款有记录归属及完整提取完成记录；每条主张有出处 | §12.3、§13.2；不证明语义已提全 |
| 称谓闭合 | 已识别称谓有绑定、出处，目标主体可解析 | 不承诺发现未识别称谓 |

节点已经存在不等于相关条款完整提取。对账通过不宣称一条条款中的所有语义均已被提全，也不增加事件专门补提或模型互查流程。

验收继续使用未参与词表归纳的真实合同与既有规则考卷：机器独跑、机械对账、只读库作答、离线判分。具体测试应验证记录能保留真实合同中的条件、否定、例外、分期对应、共同金额和原文出处，不能只验证 JSON 能够解析。

## 12. SQLite 物理结构

### 12.1 公共表

字段未标可空者均为 `NOT NULL`。业务 ID、版本 ID、哈希和 JSON 用 `TEXT`；序号用 `INTEGER`；原件用 `BLOB`。JSON 由标准库递归校验，SQL 约束负责键与引用完整性，不依赖 SQLite 扩展或图数据库。

| 表 | 列与主键 | 约束 |
|---|---|---|
| `case_info` | `case_id` PK、`created_at`、`tool_version`、`schema_version`、`value_format_version`、`code_version`、`vocabulary_hash`、`unit_config_json`、`unit_config_hash`、`vocabulary_files_json` | 每库一行，开工写入后只读 |
| `vocabulary_units` | `unit_id` PK、`entry_json` | 完整冻结条目 |
| `vocabulary_slots` | `slot_id` PK、`entry_json` | 完整冻结条目 |
| `vocabulary_assignments` | `unit_id`、`slot_id`，联合 PK | 分别引用前两表，开工后不变 |
| `submissions` | `submission_id` PK、`sequence` UNIQUE、`content_hash` UNIQUE、`submitted_by`、`phase`、`input_json`、`receipt_json`、`created_at` | 仅保存成功提交，管理顺序不表达法律优先性 |
| `objects` | `object_id` PK、`kind`、`created_submission_id` FK | 对象类别终身不变 |
| `record_versions` | `record_id` PK、`object_id` FK、`revision`、`previous_record_id` 可空 FK、`submission_id` FK、`status`、`withdrawal_reason` 可空、`data_json` | UNIQUE(`object_id`,`revision`)，版本号为正整数；status 为 active/withdrawn |
| `assertion_sources` | `record_id` FK、`path`、`source_json`，联合 PK | `path` 是相对记录数据的 JSON Pointer，记录字段与依据的对应 |
| `record_links` | `record_id` FK、`path`、`target_object_id` 可空 FK、`target_record_id` 可空 FK，前两列联合 PK | 两种目标恰有一种；由工具扫描所有引用生成，agent 不另填一遍 |

`record_links` 是引用的数据库索引，不是另一套语义关系；有法律含义的引用仍是第 12.2 节的 `reference` 记录。它使隐藏在条件、算式、参与者列表、来源前提中的引用也能做类型检查及反向查询。

**完整 DDL 见 [spec.md §7](spec.md#7-完整物理表定义)**，取代此前只有 objects/record_versions 的示意片段。该定义包含所有公共表、类型表、完成与报告表、索引及当前记录视图；case_info 的 singleton/contract_object_id、来源 level 等物理列也在那里确定，不留给实现者补猜。

`previous_record_id` 必须属于同一对象且版本号相差一，由事务内校验器检查；唯一后继约束再防止并发分支。SQL 视图不更新旧行，也不维护需要覆盖写入的“当前行”指针。

### 12.2 类型表与记录数据

每个类型表用 `record_id` 同时作 PK 和到 `record_versions` 的 FK。`data_json` 是完整版本，类型表保存其中需要检索和约束的列；两者由同一写入函数生成，不接受两份独立输入。

| `kind` / 类型表 | `data` 必填字段 | 可选字段与约束 |
|---|---|---|
| `material` / `materials` | `name,media_type,content_hash,registered_order` | `original_path`；另有 `original_bytes` BLOB，仅登记接口读入，后续不可改 |
| `text_version` / `text_versions` | `material,version_number,conversion_method,converter_version,text,text_hash,anomalies` | 登记后不可改；`material` 指素材对象 |
| `clause` / `clauses` | `text_version,sequence,text,start_offset,end_offset,tags,classification` | `original_number`；初始 classification 为 `unclassified`，后为 `ordinary/no_content/unmatched` |
| `anchor` / `anchors` | `clause,quote` | `occurrence`；`clause` 固定到条款记录版本 |
| `node` / `nodes` | `node_kind` 及对应节点内容 | 五类节点见下文 |
| `relation` / `relations` | `relation_kind,unit_id` 及对应端点 | `modality` 可空；`relation_kind=party` 时 `parties` 恰为两项；`contract` 时 `subject` 指合同节点 |
| `detail` / `details` | `owner,slot_id,value` | `owner` 指关系对象；槽须适用于该关系单元或为通用槽 |
| `reference` / `references_data` | `reference_kind,from,to` | `scope`、`label`、`exclude`、`term` 按引用类型使用，见下文 |
| `gap` / `gaps` | `clause,gap_kind,description,reported_by` | clause 及可选 related_object 固定发现时记录版本；suggested_unit_id 按冻结词表；创建后不可修订或当作工单流转 |
| `no_content` / `no_content_records` | `clause,reason` | 否定“有规定内容”的归类也带出处，不使用全局空值代替 |

节点 `data`：

- `subject`：`canonical_name`；`identifiers` 默认为空列表，每项为 `{scheme,value}`，规范名及各标识分别有依据。
- `event`：`name,description,participants`；参与者项为 `{subject,role}`，`subject` 引用主体，`role` 是原文角色；可选 `object,batch_or_stage`。
- `defined_value`：`name,value`；可选 `scope`，范围用目标引用列表，未写即本案合同范围。
- `external_benchmark`：`name,description`；不含现实数值字段。
- `contract`：可选且须有依据的 `name`；当事人、交易角色、构成文件通过带出处的引用记录表达。开工仅创建空容器，不断言法律名称；本案只有一个容器节点，不随每个 unit 重建。

当事人项结构为 `{"subject":{"object_id":"…"},"nature":"obligor","functional_labels":[]}`。每个端点主体、核心性质、非空功能标签、`unit_id` 和非空 `modality` 都需要依据。核心性质只检查八值范围，不强制其与模态匹配，也不检查两端必须是哪一对。

引用类型及方向：

| `reference_kind` | 方向与专属字段 |
|---|---|
| `appellation` | `from` 指原文条款固定版本，`label` 为已识别称谓，`to` 指主体；可选 `scope` 指材料或合同；每个称谓出现位置由其锚定位 |
| `role` | 合同 `from` → 主体 `to`，`label` 为买方、卖方等交易角色 |
| `composition` | 合同 `from` → 素材 `to`，`label` 表达原文中的文件角色 |
| `definition` | 规定或条款 `from` → 定义值 `to`，`term` 保留术语 |
| `event_of` | 事件 `from` → 其所指的关系 `to`；只在文本支持该对应时填写 |
| `scope` | 承载限定的记录 `from` → 适用目标列表 `to`，不适用目标列表 `exclude`；至少一个列表非空 |
| `priority` | 优先规定 `from` → 被优先于的规定 `to`，只保存文本明示次序 |
| `amendment` | 被修改条款或规定 `from` → 修改文本或规定 `to`；不参与记录版本折叠 |
| `redirect` | 同类别节点 `from` → 同一对象的规范节点 `to`，来源为明示依据或带前提的推断 |
| `distinct` | 节点 `from` → 被判为不同对象的节点 `to`，记录区分依据 |

字段中允许对象或记录引用的范围由上表确定；`scope` 的目标可固定到具体细节版本及值路径，使用 `{"record_id":"…","value_path":"/value/fields/…"}`。这是固定版本引用的可选路径限定，路径必须存在；稳定对象引用不允许附数组位置路径。除明确的列表字段外，`from/to` 均为单个引用。称谓可以按每个出现位置分别记录，不靠字符串替换绑定整篇同名词。

`gap_kind` 取 `unmatched_unit/missing_slot/structure_anomaly`，分别对应未匹配单元、疑似缺槽与切分异常；这是一组报告类型，不是处理状态。来源级 III 的推断前提或原文锚构成其证据。纯字符结构异常由脚本提供条款、区间及原始文本依据，不要求其证明法律含义。

### 12.3 依据、完成记录与报告

交换文件的 `evidence` 是 `[{"path":"/unit_id","source":{…}}]`。业务断言字段必须被相应来源覆盖；来源可覆盖一个内容一致的子树，混合依据时细分路径。管理字段、ID、哈希、原始文本副本及锚自身不要求再给自己造锚。关系必须分别覆盖两个端点和单元；细节必须覆盖值及槽归属判断；节点的有内容字段和解释性引用必须有依据。

新增的流程存储仅承接既有产物：

| 表 | 内容 | 行为 |
|---|---|---|
| `case_overviews` | 概要 ID、所覆盖材料与文本版本清单、正文、作者、创建顺序 | 每次通读产物追加；无来源级，不充当证据 |
| `extraction_completions` | 提交 ID、条款对象 ID、提取所读条款版本 ID | 只在关系提取文件成功提交后写入；事件文件不写此表 |
| `reconciliation_reports` | 报告 ID、所检查提交顺序、检查范围、规则版本、结果 JSON | 每次对账追加，旧报告不改 |

阶段进度由已存在的素材、条款、标签、概要、事件提交、完成记录与报告直接查询得到。skill 的任务分配表保存为普通 JSON 工作文件，含负责条款、上下文条款、结果文件路径；其进度以数据库回执为准，不另建需要人工推进的状态机。

覆盖记录是成功提交的历史事实。条款文本或边界后来修正时，旧完成记录不自动证明新内容已提取；完整重跑文件重新声明 `covered_clauses`，并对既有对象逐项修正或撤销。仅标签变化而文本和地址不变，可保留原提取覆盖。禁止把“换文件名重提”当作重新提取的去重机制。

### 12.4 索引、事务与文件移交

建索引：记录的对象/版本、关系的单元与当事人 ID、细节的所属关系与槽、引用的类型及两端、锚的条款版本、条款的文本版本与序号、缺口的类型与条款、来源级、反向引用目标。JSON 中嵌套值先按上述索引缩小范围，再由标准库计算过滤；无需全文检索扩展。

写命令使用一个 SQLite 事务，显式启用外键，事务内重新检查最新版本。主会话串行提交，不让提取 agent 持有写连接。保持 SQLite 常规回滚日志方式，不采用需要单独交付 WAL 文件的运行约定。成功响应在提交后返回。

文件路径由调用方显式指定；不另建案件注册服务。命令退出、连接关闭后可复制一个 `.db` 完整移交；有写入活动时不直接复制文件，调用方可用 SQLite 标准备份能力取得一致副本。库内含原件、全文与推断，文件访问权限就是本项目的访问边界，不增设账户系统。

案件格式版本不受支持时，命令给出实际/支持版本并拒绝写入，不尝试静默迁移。受支持的旧格式按相应解释器读取；迁移工具不纳入本版设计。词表和单位含义按案内冻结配置解释。

## 13. 校验算法与值格式契约

### 13.1 写入检查次序

1. 严格解析 JSON，检查格式版本、目标案件、字段名及基本类型，生成内容哈希。
2. 查询成功回执；已提交内容直接返回原结果。
3. 为新对象及新版本分配 ID，构造“库内当前数据＋本批变更”的候选视图。
4. 检查修正前驱、词表归属、引用可解析性及目标类型；扫描所有嵌套值与依据中的引用。
5. 校验锚、值结构、格式契约与必需字段依据；推断链检查其所有分支最终有原文依据，拒绝无依据环。
6. 检查同批对象约束，记录具体错误；有任何错误，事务回滚，返回整份失败。
7. 写入对象、版本、类型数据、来源、引用索引及允许的完成记录，在同一事务保存回执后提交。

纯校验阶段也使用同一数据库一致视图；通过校验不代表预先占有 ID，正式结果以提交成功回执为准。错误数量可设输出上限，响应标明是否截断，不能因未展示的错误被忽略而写入。

### 13.2 六查的具体口径

| 检查 | 算法 | 失败或提示 |
|---|---|---|
| 字符覆盖 | 按文本版本排序当前条款，首起点为 0，相邻边界相等，末终点等于全文长度；每段严格等于原文切片，拼接再次比较 | 丢字、重复、错序为错误 |
| 锚 | 对记录引用的固定条款版本执行 §3.4 搜索；版本存在且地址可达原件 | 不存在或歧义为错误；历史依据按其原版本检查 |
| 值枚举差异 | 从全文字符位置扫描阿拉伯数、小数、带分组符数字、百分数、明确年/月/日写法；与该位置已有量/时值的来源片段对应，列出未对应位置及原文 | 一律为提示；编号、页码等同样可能出现，报告不自动解释为漏提 |
| 值往返 | 对每个 II 级值，用指定变换解析表层并比较归一结果，再用格式参数还原，要求等于原表层 | 不支持的变换、不一致为错误 |
| 归类覆盖 | 每个范围内条款有完整提取完成记录；同时存在锚定的业务记录、缺口或无规定内容记录；反查每条业务断言的依据 | 前置事件、空提交和未打标不能独自算完成；不证明语义提全 |
| 称谓闭合 | 遍历已提交 `appellation`，检查称谓锚、绑定依据、主体目标；核查关系端点与事件参与者所用称谓依据 | 未绑定、无依据、目标错误为错误；未被识别的称谓不在机械检查承诺内 |

值候选识别器规则随工具版本记录；不以不可靠的自然语言数字理解宣称穷举所有值。比较按位置及出处关联，不只比较数字字符串是否在别处出现，也不把“原文写了值，但模型已有缺口记录”自动当作未登记。差异列表可以附关联缺口，性质仍是提示。

对账默认检查当前业务对象和它们实际引用的历史证据；全历史审计需显式指定历史范围。旧版本被取代不造成“重复提取”；旧锚也不因标签版本改变失效。

对账报告分别列 `errors` 与 `notices`。零错误可通过，值枚举提示数量不改变通过结果。按 decisions §1.21，有错误仍可查询、登记和修正，但本轮不能报告完成。报告记录所检查的提交序号；后续任何提交都会使旧报告不能代表当前库，查询显示“对账后有新写入”，需要再次对账才可报告当前完成，不增加额外人工闸。

### 13.3 确定性变换

`format_contract` 为带版本的代码，参数只控制格式，不提供任意脚本：

| 代码 | 允许变换 | 必需格式参数 |
|---|---|---|
| `decimal.v1` | 数字表层与十进制量之间转换；支持明确的十进制倍率，如万→10000 | 小数位数、分组符、符号、单位表层、倍率、前后空白及单位位置 |
| `date.v1` | 明确年/月/日或年/月格式与相应精度日期之间转换 | 分隔写法、各段位数、精度、前后字面量 |

来源 II 的公共字段为 `level:2,anchors,surface,format_contract,format_parameters`；归一结果位于该来源覆盖的值字段。`decimal.v1` 的参数为 `decimal_places`（非负整数）、`group_separator`（空串或明确分组符）、`decimal_separator`、`sign_style`（`minus/plus/none`）、`scale`（正十进制字符串）、`unit_surface`、`unit_position`（`before/after`）、`prefix`、`suffix`、`number_unit_separator`。这些字符串逐字保存格式，数值部分必须由解析结果生成。不能将整段数字藏进 prefix/suffix 而令真正数值不参与还原。

`date.v1` 参数为 `precision`、`component_widths`、`separators`、`prefix`、`suffix`，例如日期组件位数 `[4,2,2]`、分隔符 `["-","-"]`。组件数量按精度校验；中文字面量年/月/日按 separators 和 suffix 保存。其他字符组合不靠宽松替换吞掉。

参数保存实际表层中的格式信息；规范值改变后不能靠保存一份原文常量假装往返成功。先从表层独立解析出值，比较归一值，再根据值和格式参数重建表层，两方向都验证。格式程序不联网、不执行用户代码。

中文大写金额、含糊日期及其他未支持写法不伪装成 II 级机械变换；保留原文并按 I 级表达，有解释推断时按 III 级记录。具体新增变换属于格式能力扩展，带版本和相应样例。

### 13.4 切条款与表格

切分以已确认的 `scan_structure` 识别为候选，参照 contract_v3 的层级渲染与完整 article 分组行为确定真正的 article 范围：有章节时章下一级是常规分析单位，无章节时第一层合同条目是常规分析单位。空行、软换行交叉引用和表格内部不产生独立 article。编号跳跃、重复、混用及无法判定归属的区域生成结构异常缺口，不改变字符。无编号连续内容必须显式成为有地址的区间，不能被静默丢弃；无编号不自动等于异常。

转换后的表格保留为连续文本；没有条款编号的表格按原文所在段或连续表格区域编号，行列关系由原样 Markdown/文本和值的重复组保存。条款锚仍按连续引文搜索，不发明原件中的单元格坐标。需要保留的表格结构如果已在转换时丢失，作为预处理异常报告，入库工具不能恢复不存在的信息。

## 14. 交换文件与返回值

### 14.1 通用写入格式

```json
{
  "format_version": 1,
  "case_id": "目标案件 ID",
  "vocabulary_hash": "本案快照哈希",
  "submitted_by": "agent 或人员标识",
  "phase": "extraction",
  "covered_clauses": [{"object_id":"条款 ID","record_id":"读到的条款版本 ID"}],
  "records": [],
  "issues": []
}
```

`phase` 是提交用途 `preparation/tagging/extraction/correction`，用于区分既有流程产物，不是流转状态。`covered_clauses` 的项是覆盖描述，两个 ID 都必填并相互核对，**不是** §2.2 的单目标引用格式。只有 `extraction` 的条款列表产生完整提取完成记录。其他用途列表为空，涉及哪些条款由记录本身追溯。

每个声明完成的条款须在本批至少有一条对应的非锚建模记录、缺口或无规定内容记录，依据能回到该条款；只有前置事件、空 `records` 或空锚不能取得完成记录。此规则检查提取提交确有对应产物，仍不证明该条款的语义全部提全。

新增对象：`{"local_id":"唯一临时编号","kind":"detail","data":{…},"evidence":[…]}`。

修正对象：`{"local_id":"本批唯一编号","object_id":"已有对象 ID","previous_record_id":"当前记录 ID","kind":"detail","data":{…},"evidence":[…]}`。

每条记录必须有 `local_id`；`object_id/previous_record_id` 要么都缺席（新建），要么都提供（修正）。`data` 为完整字段，未填写可选字段不沿用旧值。锚等仅定位原文的记录使用空 `evidence`。来源中临时引用必须能按所需固定版本规则解析。

正常记录可省略 `status`，工具写为 `active`。撤销版本显式提供 `status:"withdrawn"`、`withdrawal_reason` 及原完整 `data/evidence`，同时提交所需依赖修正。不存在“只删一行”的输入。

`preparation` 文件可有可选 `overview`：`{text_versions:[引用],body:文本,authored_by:署名}`；主会话随准备结果同批保存案件概要库存份。它不是业务记录，不需要伪造证据，也不算条款提取完成。

`issues` 为 agent 返回主会话的问题摘要；词表缺口必须同时进入正式 `gap` 记录，不能只留在摘要。没有发现问题时使用空列表。

### 14.3 成功、重复与失败

成功返回：

```json
{
  "ok": true,
  "replayed": false,
  "submission_id": "submission-uuid",
  "content_hash": "sha256",
  "id_map": {"payment":{"object_id":"relation-uuid","record_id":"record-uuid","revision":1}},
  "counts": {"relation":1,"detail":1,"anchor":1,"reference":2},
  "covered_clauses": ["clause-uuid"],
  "issues": []
}
```

示例 `id_map` 为节选，实际响应包含全部待写记录，包括修正后新版本的映射。重提返回相同回执内容与 `replayed:true`。失败不含已落库 ID，也不含部分成功数量：

```json
{
  "ok": false,
  "errors": [{
    "code":"ANCHOR_NOT_FOUND",
    "path":"/records/0/data/quote",
    "local_id":"source",
    "message":"引文未出现在所指条款版本中",
    "target_record_id":"clause-version-uuid"
  }],
  "errors_truncated": false
}
```

稳定错误代码包括 `INVALID_JSON/UNSUPPORTED_VERSION/CASE_MISMATCH/VOCABULARY_MISMATCH/DUPLICATE_LOCAL_ID/REFERENCE_NOT_FOUND/REFERENCE_TYPE_MISMATCH/STALE_REVISION/INVALID_VALUE/MISSING_SOURCE/ANCHOR_NOT_FOUND/ANCHOR_AMBIGUOUS/ROUNDTRIP_FAILED/DATABASE_ERROR`。消息可中文，调用方据代码分支；路径使用 JSON Pointer。

### 14.4 共同约束、例外与阶段对应的表示示例

- **共同总额**：甲→丙、乙→丙两条付款关系；共同总额作为一个定义值；两条关系均有指向它的细节。再以一项合同规定及 `scope` 引用明确共同总额适用于这两条关系，细节保存“任一方付清则两项义务均终止”的条件及原文。“任一方付清”使用前置事件记录，不能擅自拆为两笔各自独立的债务。
- **局部例外**：限定规定的细节值保存原文与必要条件，`scope.to` 指付款条件细节，`scope.exclude` 指质量依据细节；若只针对复合值的一项，引用固定细节版本并加 `value_path`，不扩大到全部关系。
- **分期对应**：每个阶段在一个复合列表项内保存阶段名、金额/比例、条件及期限，避免把所有条件和所有金额分别铺成两个无对应的列表。若阶段独立构成不同关系，则分别建关系并引用各自条件。

上述结构给出承载方式；相应槽不存在时报告缺口，不由工具自动创设“共同约束槽”或其他词表条目。消费者能读到限定内容和准确目标；本项目不据此结算实际余额或判断义务已履行。

## 15. CLI 接口

案件/词表命令名称及入口组织已由用户确认（decisions §1.23）；统一预处理入口见 decisions §1.32。本章描述目标接口，精确参数组合、默认值、输出和退出条件见 spec §9。实现已开始，包代码放 legal/src/legal，从 legal/src 运行三个模块入口；skill 的数据路径按 spec §1.5 解析。

### 15.1 案件 CLI

安装入口为 `legal-case`，从 `runtime.json` 取得其绝对路径，简称以下表内的“案件 CLI”；每个命令一个进程。开发调试仍可使用 `python -m legal.case_cli`，安装后的 skill 按 §1.5 调用。目标库均通过 `--db` 指定，不自动扫描其他案件。

| 子命令 | 参数 | 输出 |
|---|---|---|
| `init` | `--db FILE --vocabulary PATH` | 新案件 ID、合同容器 ID、冻结词表与配置哈希；目标文件已存在则拒绝覆盖 |
| `register` | `--db FILE --original FILE --text FILE --metadata FILE` | 素材与文本版本 ID；元数据含类型、转换工具/版本、异常；首次登记原件与文本一起提交 |
| `split` | `--db FILE --text-version ID` | 条款 ID、地址、字符覆盖结果、结构异常缺口 |
| `write` | `--db FILE --input FILE` | 第 14 章回执；单记录直接参数形式见下文 |
| `query` | `--db FILE` 加过滤/选择参数 | 可追溯的结构化结果、进度或原件导出 |
| `group` | `--db FILE --output-dir DIR`，可选 `--text-version ID` | 逐字分组文件及每份文件的条款清单；不生成文本版本 |
| `reconcile` | `--db FILE`，可选 `--text-version ID`、`--history` | 指向记录/字段的六查报告及报告 ID |

单条记录可用 `write --kind KIND --local-id ID --data-json JSON --evidence-json JSON --submitted-by NAME`；修正时另加 `--object-id ID --previous-record-id ID`，可加 `--status withdrawn --withdrawal-reason TEXT`。CLI 包装成同一写入结构，语义、校验、回执与文件输入一致。复杂互引仍用完整文件，主会话不拆成逐行命令。

`register` 的 `metadata` 包含可选 `material_id`：重转换指向原素材并新增不可变文本版本，核对原件哈希；首次登记省略该字段。登记哈希包含实际原件字节哈希、文本及元数据内容，不含临时文件路径。`split` 同一文本版本和同一算法版本重复调用返回原切分结果；已存在条款时不自动覆盖或按新算法重切。

一般条款边界修正使用既有追加/撤销路径：一对一修正沿用对象 ID；拆并条款撤销旧对象、新建片段，并调整现存业务引用及覆盖记录。原文及旧锚固定版本仍保存。不得仅为重跑改写原件或文本版本。

### 15.2 查询与导出

通用过滤参数：`--kind`、`--party OBJECT_ID`、`--unit UNIT_ID`、`--slot SLOT_ID`、`--source-level 1|2|3`、`--clause OBJECT_ID`；同类参数可重复取并集，不同类条件取交集。按槽查询关系时要求它至少有一条当前细节匹配；来源级按命中的具体字段/细节筛选，不能把一条含 III 级字段的关系整体标成 I 级。

选择参数：

- `--object ID` 默认取最新版本；`--record ID` 取指定历史版本；`--history` 列历史，`--include-withdrawn` 显示撤销对象。
- `--view records|materials|clauses|vocabulary|overview|events|progress|gaps|report` 选取既有内容。`progress` 返回各阶段已有产物和未完成条款，不推进流程。
- `--limit N --offset N` 分页，按对象创建顺序及 ID 稳定排序；响应包含匹配数及下一页位置。
- `--format json|markdown` 默认 JSON；Markdown 供阅读与审阅，不反向充当写入格式。`--output FILE` 写出文件，已有目标不覆盖，调用方使用新路径。
- `--view materials --object ID --format original --output FILE` 导出原件字节并返回哈希；此方式不与记录过滤组合。

默认结果含对象/记录版本 ID、当前数据、字段来源级、出处引文、条款地址及原件 ID；长篇全文按条款单独查询。重定向保留原 ID 与解析目标；有冲突时明确列候选，不任取一项。

查询结果区分：`found`（有匹配记录）、`no_record`（本查询无记录）、关联 `gaps` 及缺席槽列表。未提取条款、未通过/尚未更新的对账状态一并可见，不能把无记录直接转述为合同没有约定。缺席槽指“模型未填”，不能机械断定是原文未约定。

### 15.3 词表 CLI

安装入口 `legal-vocab`，实际执行路径取自 `runtime.json`；`--vocabulary PATH` 指向全局词表文件或目录。开发模块入口为 `python -m legal.vocab_cli`。

| 子命令 | 参数 | 行为 |
|---|---|---|
| `init` | `--vocabulary PATH` | 建空结构；不内置法律单元和槽，不覆盖已有词表 |
| `list` | `--kind unit\|slot\|assignment` | 列条目及归属 |
| `show` | `--kind unit\|slot --id ID` | 条目全文及关联 |
| `add` | `--kind unit\|slot --entry-json JSON`，槽可重复 `--unit ID` | 校验后新增，已有 ID 不覆盖；无归属的新槽明确为通用槽 |
| `remove` | `--kind unit\|slot --id ID` | 删除；存在归属处置要求时拒绝单独删除，改用完整变更文件 |
| `diff` | `--left PATH --right PATH` | 结构化列新增、删除、归属变化及同 ID 内容变化；同 ID 内容变化标为违规 |
| `aggregate` | `--cases FILE --output FILE` | `cases` 为显式案件路径列表，只读缺口及相应冻结词表/出处，形成回流报告 |

混合增删通过 `legal-vocab --vocabulary PATH --input CHANGE.json`，执行时将命令名替换为安装信息中的绝对路径；顶层为 `format_version`、`expected_hash`、`operations`。`operations` 是已有 `add/remove` 原子动作的列表；按整份最终结果校验，全部通过才替换词表文件。首版正式词表采用已允许的单文件布局；读取和比较可加载目录，写操作要求单文件。写入同目录临时文件、刷新后以 `os.replace` 替换正式文件，失败不留下部分条目更新；不引入多文件事务或词表发布服务。

删除导致槽失去全部归属时，变更文件另有 `orphan_slots` 显式清单：每项为 `slot_id` 加 `disposition=remove/reassign/general`；`reassign` 须给出新 `unit_ids`。工具不据此改变槽内容；若改变含义，仍新增新 ID 并删除旧条目。`expected_hash` 必须与当前词表一致，防止基于旧审阅结果覆盖后来变更。

`operations` 的新增项为 `{action:"add",kind:"unit|slot",local_id,entry,unit_ids?}`：`entry` 不含 ID，由工具生成并在回执映射；`unit_ids` 仅适用于槽。删除项为 `{action:"remove",kind:"unit|slot",id}`。`unit_ids` 项可以是已有 ID 字符串，也可以是 `{local_id:"同批新增单元编号"}`。`local_id` 在变更内唯一，工具先分配全部 ID 后校验最终词表。单条 `add` 同样不接受调用方覆盖 ID。

文件格式例（条目名称仅为示例）：

```json
{
  "format_version": 1,
  "expected_hash": "当前词表哈希",
  "operations": [
    {"action":"add","kind":"unit","local_id":"u1","entry":{"name":"示例单元","description":"经人工审定的识别说明"}},
    {"action":"add","kind":"slot","local_id":"s1","entry":{"name":"示例金额","description":"经人工审定的槽说明","value_schema":{"one_of":[{"form":"quantity"},{"form":"reference","target_kinds":["node:defined_value"]}]}},"unit_ids":[{"local_id":"u1"}]}
  ],
  "orphan_slots": []
}
```

词表回执包含 `ok,before_hash,after_hash,id_map,changes`，`id_map` 映射本批编号至正式条目 ID。没有明确处置的孤立槽、非法同 ID 改写、缺失目标或不匹配哈希均返回错误且不改正式文件。单条直接命令在同一次执行中读取当前哈希并使用同一校验路径。

聚合以当前全局词表为对照，原案件的单元/槽解释保留其冻结快照；不同快照同名条目不擅自对齐。报告包含案件、缺口类型、原文证据和本案词表哈希，建议部分由治理 agent 结合当前词表撰写。对账未通过案件可以列入报告，但附其当前质量状态，不伪装为已验收语料。

词表工具写文件与版本控制提交分开：工具返回内容差异和哈希，git 提交/推送沿用项目协作约定，不自动执行。没有已授权发布动作时，不将生成文件等同于已经发布。

### 15.4 预处理 CLI 的对接与退出码

预处理的源码入口为 `legal/src/legal/preprocess_cli.py`，安装命令为 `legal-preprocess`。以下命令名在实际执行时替换为安装信息中的绝对路径：

```text
legal-preprocess --input FILE --output-dir DIR --converter-config FILE
```

转换配置是包含 format_version 与 argv 数组的 JSON；显式指定外部程序，通过完整参数 `{input}`、`{output_dir}` 传入原件和临时输出目录，不经 shell。外部程序负责实际格式转换，统一入口校验 `text.txt` 与 `metadata.json` 后发布至指定目录，返回路径、原件/文本哈希和异常。配置、两文件协议及失败规则见 spec §9.7。

案件 skill 用这两个文件调用 register，再由案件 split 切条款；初始化 skill 可直接消费转换结果作为归纳语料。预处理不生成案件 ID、标签或关系；本项目不把任意 PDF/Word/OCR 转换承诺为标准库能力。预处理 skill 的入口只说明与调用该工具，实际转换引擎由环境配置。

stdout 只返回机器可读结果，进度写 stderr。退出码约定：`0` 操作成功；`2` 输入/参数/业务约束校验失败；`3` 文件、数据库或外部转换进程故障；`4` 对账已执行但发现错误。只有提示的对账返回 `0`；失败回执仍给出结构化错误。该约定不改变“允许带着对账错误继续操作”的裁决。

## 16. 四个 skill 的交接与恢复

### 16.1 共用文件约定

skill 使用调用方指定的工作路径保存输入清单、读手产物、人工审阅文件与工具回执。正式数据以案件库或全局词表为准，工作目录不是第二个状态数据库。新合同入库须先按 spec §1.6 创建独立的 `contract-...` 合同工作目录并使用固定组织和命名；初始化词表和词表治理的工作文件仍可按任务组织。目录与文件名不作为自动状态切换信号。

所有 skill 文档均须有“工具用法”部分，说明实际命令、参数、产物、错误返回及如何继续；尚未实现的命令不能在运行说明中写成可立即执行。

四个 `SKILL.md` 及其必须携带的参考文件见 spec §1.3—§1.4。首版保持宿主通用：从入口真实位置找到安装根，读取共用说明与 `runtime.json`，使用已绑定的绝对命令路径启动专用环境中的 CLI。绑定与失败规则见 §1.5、spec §1.5；主会话向读手提供说明及实际输入/输出路径，模型会话不因读取 skill 而切换 Python 环境。合同工作目录继续按下列流程组织。

大量合同阅读交给 sub-agent；主会话接收结构化文件、摘要及条款清单。读手只能输出到分配的文件，不直接改案件库或正式词表。

### 16.2 预处理 skill

入口：`src/skills/legal-preprocess/SKILL.md`。输入：原件路径、指定输出目录、转换配置路径。执行：读取共用预处理用法，调用统一预处理 CLI，由其启动已配置转换程序并校验结果。输出：原件、文本、元数据路径、哈希及异常摘要，交回调用 skill；完整格式见 spec §9.7。

该 skill 不判断法律关系、不掩盖 OCR 异常。格式不支持或转换失败就返回具体错误；是否重转换、换源件由调用方依既有异常处置规则处理。入库 skill 判断质量已妨碍阅读时向用户取得更好源件，不将无法读出的内容编入模型。

### 16.3 入库 skill

| 次序 | 主会话与工具 | 读手输入/产物 | 继续条件 |
|---|---|---|---|
| 0 新合同建目录 | 在工作根目录排他创建 `contract-...` 合同工作目录，复制原件、词表、转换配置；续做同一合同沿用原目录 | 暂无正文阅读 | 以后所有入库输入副本与产物均有确定的合同工作目录内路径；详见 spec §1.6 |
| 1 开工 | `init` 冻结词表，或查询明确指定的已有库 | 无正文阅读 | 取得案件 ID 和词表哈希 |
| 2 登记与切分 | 预处理 skill → `register` → `split` | 异常必要时交读手解释，主会话读摘要 | 原件、全文、条款可查询；切分守恒 |
| 3 初读准备 | 固定版本并准备连续阅读材料；派分段读手，收齐笔记后交一个归纳读手；主会话对最终 preparation JSON 调用 `write` | 各段产出带出处的阅读记录；归纳读手统一形成概要、主体与事件；单段时由同一读手兼任 | 主读范围实际读全，问题有明确处置，准备结果成功写入，正式共用记录可交接；详见初读设计 §8 |
| 4 打标 | 按不相交条款批次并行派发；逐文件 `write` | 案件概要、冻结单元、负责条款；产出完整条款修订、无匹配缺口 | 本轮条款全部有分类；普通条款 tags 非空 |
| 5 分组及分配 | `group`，主会话写任务清单 | 每条款分配一个完整提取责任任务，多标签副本只作上下文 | 负责集合不重叠，合并等于本轮范围 |
| 6 并行提取 | 按完整条款主责派发并收结果，unit 仅提供分组上下文 | 概要、事件及 ID/出处、已知其他共用对象、负责条款、分组上下文、冻结词表、输出格式；产出 extraction JSON + 路径/数量/问题摘要 | 提取范围不受组标签限制 |
| 7 统一提交 | 处理摘要及 issues 中明确的未完成/矛盾；每文件一次 `write`，保存回执；失败送回原读手修正整份 | 问题说明、错误代码、字段路径及必要现存记录 | 全部负责条款有成功提交；已知语义错误不能凭回执成功宣称解决 |
| 8 对账 | `reconcile`，据报告按既有修正接口处理 | 必要时读手修正具体记录；无另设核对员 | 当前对账零错误，提示单列 |

“无规定内容”或“无匹配”的条款也必须被分配完整提取责任；可随某个读手的负责清单交付，不因无 unit 标签被漏掉，不为其新增词表单元。最终按内容形成无规定内容记录或缺口等产物。

关系提取任务清单可记录 `task_id,unit_id,responsible_clauses,context_clauses,input_files,output_file`；其中 `unit_id` 对无匹配任务可空。`task_id` 是工作文件标识，不进入法律关系模型。主会话在派发前机械比较负责条款集合，保证每条一次。初读的主读范围和阅读记录按下述专项设计组织，不产生完整提取完成记录。

初读按 decisions §1.40 采用 [合同初读工作流设计](initial-reading-design-2026-10-02.md) §1—§9，具体分配算法、任务材料、笔记内容、归纳步骤、概要栏目及恢复规则以该文件为准。它细化 §1.39 的顺序阅读和带问题回读：各段内部按原文顺序阅读，段与段可以并行；主会话先准备完整材料，归纳读手统一承担主体与事件认定。每任务目标正文量的首版初值为 20,000 个 Unicode 字符，可按模型和工具能力调整；超长单条仍交一个读手，阅读分窗不改变条款边界。

各段记录保留局部事实、定义、共同限定、条件与时间联系的原句及跨段问题，不分别建立正式事件。归纳读手根据原文依据统一判断粒度和同一性，必要时定向回读或退回补充，产出一个 preparation JSON；`covered_clauses=[]`。阅读笔记不能作为正式断言的来源前提，概要仍是背景。阅读及问题记录放在合同 `tasks/`，正式提交、回执和查询交接位置按初读设计 §7。

准备结果写入成功后交付完整 query 记录，保留 data、正式 object_id／record_id、evidence 与 provenance；不能用仅有 ID 和名称的简表代替。关系任务引用正式 `extraction.md` 和数据格式，不临时重写缺口或来源规则；冻结词表含单元定义、槽和归属，槽表不能代替完整快照。运行时初读说明须承载上述职责和必要规则，安装后的执行不依赖仓库 `docs/`。内部材料导出辅助不增加 CLI 命令或任务状态库。

本轮按[工作流小幅优化](workflow-optimization-2026-10-02.md) §2—§6 细化上述环节：派发以完整条款主责为中心；运行说明明确“专属槽加通用槽”；同一提取读手先识别规定和完整限制，再选单元/槽并组织 JSON；归纳读手按原文条件/时间的使用位置核对事件；主会话在已有接收环节处理明确暴露的未完成事项。任务和提交字段不变，精确约束见 spec §10.3.2。写入及六查通过是机械结果，已确认可表达却仍未处理的内容须修正或明确交接未完成；真实限制不要求全部清空，也不增加自动语义校验或新的质量字段。

恢复时先查询库：有成功回执的文件不重提取，响应丢失时重提原文件取回回执；失败文件按原错误继续修正。已完成对象的重跑须读取其 ID 与版本，提交修正/撤销，不另建一套同义记录。工作目录丢失时可从库导出素材、概要、事件和未完成条款重新分配。

初读中断及新增材料按初读设计 §7.3 处理：对应版本一致的已完成笔记可复用，未完成范围续做；新材料主读、受影响旧材料定向回读，归纳时读取既有主体和事件并沿用身份与追加规则。新增材料仍走登记、切分、初读准备、打标、分组和提取。事件遗漏仍按已接受的质量边界处理，不附加专门补提环节。

### 16.4 初始化 skill

语料用途由用户事先指定（decisions §1.24）：归纳语料、规则考卷、未参与归纳的真实验收合同。agent 不擅自把考卷或验收合同改作归纳来源。规则文件帮助检验可表达性；法律文本仅作原定查漏清单，不从中直接造单元。

工作文件：

| 产物 | 内容与用途 |
|---|---|
| `corpus.json` | 用户指定的用途、合同种类/来源、原件路径与哈希、转换文本路径与哈希、转换元数据；不要求此时已有案件词表或案件库 |
| 第一遍读手文件 | 每条款的主题、可约定点、原文摘句、当事方、原文模态词；含语料文件、字符位置、引文作为证据地址 |
| `units-review.md` | 候选单元、三项资格判断、吸并建议、跨种类证据及原文地址；用户直接写意见 |
| `units-approved.json` | agent 按第一道人审意见整理的定稿单元，供第二遍使用；不是新人工审批表 |
| 第二遍读手文件及 `slots-review.md` | 按单元的槽、值结构、真实例句、归属、条件适用标记；用户在结果中写意见 |
| 最终词表、证据包、判定表 | 按第二道人审意见整理；残留条款、考卷表达结果及法律文本查漏结果一并保存 |

正式词表通过词表 CLI 生成，语料证据包保留原件/转换文本与哈希以便回查。归纳阶段的证据地址是语料文件和原文位置，不伪造尚不存在的案件 ID。生成后的案例入库才使用冻结快照及正式案内锚。

人审只需自然语言意见；未收到意见时保持对应环节待人处理，不把时间经过视为同意。有互相冲突或无法确定的意见先向用户核实。第二遍可按既有流程逐单元重跑，仍以第一道意见整理后的单元为输入；若需改变已定单元，回到相应人工意见处理，不由读手自行改全局词表。

最终三件套按原定方式进入版本控制审阅；当前工作区没有 Git 仓库和远端，建仓、远端与发布目标属于执行时所需环境，不在本次文档任务中臆造或操作。

### 16.5 词表治理 skill

入口一：用户提供案件路径清单，主会话 `aggregate` 生成报告。入口二：用户直接提出词表变更要求。两者均由 agent 读取当前词表与相关证据，形成 `proposal.md`：问题、当前表达能力、具体增删及归属处置、证据、对旧条目的对应说明。

用户直接在建议文件写意见；agent 据此产出变更 JSON，主会话用词表 CLI 执行。若当前哈希已变化，重新对照最新内容和意见，不能盲用旧文件覆盖。原意见不能决定新冲突时再向用户核实；不增加固定周期、审批状态表或独立评审员。

返回变更前后哈希、新增/删除/归属变化、未采纳建议及理由。旧案件不回填；是否因词表缺口影响使用而重开案件，由用户结合报告决定，新案通过既有开工流程取得新快照。比较两次结果时按原始素材哈希及条款出处对应，不要求跨案件对象 ID 相同。

## 17. 实现边界与验收用例

### 17.1 模块划分与配置

目标实现为标准库 Python 包；**全部代码位于 legal/src，包括测试、SQL和辅助脚本**，七件交付物及参考文件布局见 spec §1。下列模块文件均在 `legal/src/legal/`，SQL 为 schema.sql，首版配置为 config/units.v1.json：

安装元数据为 `legal/src/pyproject.toml`，提供三个 console script 入口及包资源声明；安装辅助代码归 `legal/src/scripts`，安装验证归 `legal/src/tests`。已安装运行环境的位置由安装根确定，运行不依赖开发源码目录。四个 skill 和 CLI 须按同一交付版本安装，不能仅更新命令而继续使用另一版本的输入格式说明。

| 模块 | 职责 |
|---|---|
| `formats` | 严格 JSON、版本、规范化哈希、六值及复合结构验证 |
| `vocabulary` | 全局文件读取/校验/增删、归属处置、快照、diff 与聚合 |
| `storage` | SQLite 表、事务、对象版本、成功回执、证据与引用索引 |
| `anchors` | 字符地址、引文搜索与消歧 |
| `values` | 格式契约及十进制变换 |
| `query` | 当前/历史检索、依据展开、重定向与冲突展示 |
| `reconcile` | 六查与报告持久化 |
| `splitter` | 按已核对的 scan_structure 版本和 spec §12 实现切分与异常记录 |
| `preprocessing` | 转换配置、外部进程调用、text/metadata 校验、输出与哈希；不实现第三方转换引擎 |
| `preprocess_cli`、`case_cli`、`vocab_cli` | 三个入口的参数解析、文件入口、输出与退出码 |

模块间不内置 agent 调度，调度由 skill 执行。SQLite 层不解析法律含义；格式层不自行扩展法律词表。

单位配置使用 JSON：`{format_version,version,units:[{code,name,dimension,scale,reference_unit,aliases}]}`。`code` 唯一；`dimension` 区分币种、时间、比例、计数等；`scale` 为十进制字符串，仅描述同一单位体系的精确格式换算。币种之间不设汇率，工作日与自然日不设换算，月/年不换算为固定天数。别名是格式识别配置，不替合同判断未明确的计量规则。

时间 `relation` 在本版取 `before/after/within_before/within_after/at`；`at` 表示相对基准的指定位置，偏移可为零或原文明确的有符号量，其他形式保留相应前后/以内含义。不能由这些形式准确表达的边界保存在 `boundary_text` 或带原文的细节中，不把“以上”“不含当日”等含义硬塞为已支持的算子。算式代码为 `add/subtract/multiply/divide/min/max`，减除恰两项，其余至少两项；数值叶单位兼容性可校验，但不执行需要现实外部值的求值。

开发顺序沿用既定安排：格式与词表校验器 → 初始化 skill → 经人工审定的 v0 词表 → 案件工具及其余 skill。预处理实现独立对接。示例词表只作测试夹具，不作为工具默认内容发布。

### 17.2 必需的验证场景

| 场景 | 可观察的通过条件 |
|---|---|
| 无编号、重复编号、中文编号、表格及空白 | 拼接与全文逐字符一致，地址唯一，异常留痕 |
| 引文重复、重叠匹配与不连续引文 | 正确消歧；错误引文拒绝整份，不偷偷归一化 |
| 文件中最后一条有错误 | 此文件零写入，包括前面合法记录与完成记录 |
| 成功后响应丢失、换文件名或缩进重提 | 同内容返回原 ID/回执，记录数不变 |
| 修正文件成功后重提 | 直接返回旧回执，不因前驱已过时而失败 |
| 两份不同修正基于同一旧版本 | 先提交者成功，后提交者整份报版本冲突 |
| 条款补标签与细节修正 | 稳定对象 ID 不变，旧行和旧锚可查，默认读新版本 |
| 撤销、拆分及遗漏依赖修正 | 默认不见撤销对象；未修正现存业务引用则整份拒绝 |
| 原件移交 | 关闭库后复制单个数据库，取回原件哈希与登记时一致 |
| 模态为空、禁止行为、局部例外 | 含义通过性质/槽/值/引用可读，不因空模态被当成无约定 |
| 多方共同付款、分期条件 | 二元关系保留共同总额与终止条件，阶段内金额/条件/期限对应 |
| 前置事件与多标签分组 | 同事件 ID 被复用，事件提交不记完成，多标签条款只完整提取一次 |
| 初读分段、归纳与恢复 | 按[初读设计 §9](initial-reading-design-2026-10-02.md#9-首轮验证方法)执行短/长合同、超长单条、跨段同一事项、分包区分、原句限定及中断恢复检查；主读覆盖与实际语义分别验证 |
| 本轮工作流小幅优化 | 按[优化方案 §8](workflow-optimization-2026-10-02.md#8-下一轮验证)验证跨单元完整提取、通用槽、付款基准、完整终止条件、事件依据及明确问题处置，再做完整合同双向复验 |
| 称谓漏识别与值候选差异 | 报告不宣称找全称谓，数值差异提示不阻断 |
| 空白范本字段与缺席槽 | 显式空值、没有细节、词表缺口三者可区分，无虚构数值 |
| 删除最后归属、变更词表后读旧案 | 未明确处置则拒绝；旧案按原快照解释 |
| 对账失败及其后继续写入 | 允许操作，质量状态如实显示；旧通过报告不冒充最新结果 |
| 身份重定向冲突及文本修改指向 | 冲突展示；不按登记时间自动裁决，不把补充协议当版本纠错 |

上述是开发验收要求，确定输入、状态变化、错误代码和通过断言已在 spec §12.4、§14 展开。实现启动不等于验收通过；最终仍需未参与归纳的真实合同和规则考卷验证“只读库可以回答什么”，记录可答且对、可答但错、不可答及其出处/缺口；不以格式测试代替语义验收。

### 17.3 进入实现时的材料前提

- `contract_v3` 扫描函数源码已取得并核对，固定版本及适配要求见 spec §12；实现时按该版本复用到 legal/src 并验证，不要求运行环境依赖用户的另一个工作区。
- 按已确定的统一预处理接口配置实际转换工具并验证支持格式；本项目的零依赖约束不构成“标准库能转换全部 PDF/Word/OCR”的承诺。
- 用户提供并分配归纳语料、规则考卷与真实验收合同；实际词表通过两遍两闸生成，本次不代替律师编写领域词表。

这些是执行所需材料和环境，不是增加流程步骤。未来发现具体需求歧义或需要改变流程、机制、命令时，继续先向用户核实。
